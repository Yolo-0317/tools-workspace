# 短线交易投顾系统设计书

> 版本：v1.1（总体设计背景）
> 定位：新建的面向个人 A 股交易者的短线交易决策支持项目；目标是通过可复核的选股、价格计划与风险纪律追求长期可持续的交易收益，不承诺获利；不连接下单，不代替用户作出交易决定。

> 实施基线：[`docs/superpowers/specs/2026-08-10-short-term-trading-v1-1-design.md`](../../docs/superpowers/specs/2026-08-10-short-term-trading-v1-1-design.md)。本文件保留总体设计背景；与 v1.1 实施基线冲突时，以实施基线为准。

## 1. 目标与边界

### 1.1 目标

系统每天稳定回答五个问题：

1. 账户当前是否允许新开交易？
2. 现有持仓各自应持有、观察、减仓还是退出？
3. 收盘后哪些股票值得进入次日候选池？
4. 盘中某只候选是否触发了预先写好的价格计划？
5. 每笔交易和每条规则是否真的有效？

### 1.2 非目标

- 不自动登录或操作券商交易页面，不自动下单、撤单或转账。
- 不把收盘选股、单一消息、盘口单帧或模型分数直接解释为买入指令。
- 不承诺收益，不以回本、浮亏或预测涨停替代风险控制。
- 不把长期价值研究、公众号内容生产和短线交易决策混在同一条主链路。

### 1.3 项目边界

- 本系统是一个新项目，不以现有泛股票分析、旧选股评分或历史文档结构为设计前提。
- 现有 `stock-ai` 在过渡期仅提供可替换的数据适配：历史日线、东财 OpenCLI 采集能力与已有 MySQL；不接入 Home Hub。
- 新系统独立拥有短线交易的数据契约、缓存、候选、诊断、风控、计划与复盘逻辑；任何旧模块只有满足新契约后才可接入。
- 用户账户、风险预算和执行卡属于本地私有适配层，不随项目模块分享或提交。

### 1.4 当前风险基线

| 项目 | 规则 |
|---|---:|
| 科创资格资产目标 | 550,000 元，仅用于资格与现金缓冲 |
| 短线实投预算 | 100,000 元，所有交易风险按此计算 |
| 首次试错仓 | 2%–4%，即 2,000–4,000 元 |
| 强信号上限 | 8%，即 8,000 元 |
| 同时交易股 | 2–3 只 |
| 总交易暴露上限 | 40%，即 40,000 元 |
| 单笔计划最大亏损 | 500 元 |
| 同题材链上限 | 35% 交易预算 |
| 周度保护 | 累计亏损达到 3,000 元，下一周只复盘和观察 |

## 2. 总体架构

```text
                    ┌───────────────┐
                    │ 市场环境引擎   │
                    └──────┬────────┘
                           │ 市场可交易状态
┌───────────────┐    ┌──────▼────────┐    ┌────────────────┐
│ 短线选股引擎   │───▶│ 个股诊断引擎   │───▶│ 组合与风控引擎  │
│ 全市场 → 候选 │    │ 候选 → 价格计划│    │ 最终否决/仓位  │
└───────────────┘    └──────┬────────┘    └───────┬────────┘
                            │ 收盘计划               │ 可人工试错
                            ▼                        ▼
                     ┌──────────────┐        ┌──────────────┐
                     │ 盘中确认引擎  │───────▶│ 用户人工决策  │
                     └──────┬───────┘        └──────┬───────┘
                            │ 快照/触发记录           │ 成交结果
                            └──────────┬─────────────┘
                                       ▼
                              ┌────────────────┐
                              │ 日志与复盘引擎  │
                              └────────────────┘
```

决策优先级固定为：**风控是否允许 → 是否存在候选 → 价格是否触发 → 用户是否执行**。

## 3. 数据分层与新鲜度

| 层级 | 数据 | 来源 | 更新节奏 | 允许用途 |
|---|---|---|---|---|
| A：稳定历史 | 日线、MA、ATR、20 日高低点 | 本地 MySQL | 收盘后 | 收盘计划、回测 |
| B：收盘快照 | 筹码、公告、财务风险、主题归属 | 东财 OpenCLI / 人工核验 | 收盘后 | 次日计划 |
| C：盘中快照 | 现价、分时、量比、换手、资金、板块、盘口 | 东财 OpenCLI | 盘中按需 | 触发验证 |
| D：账户事实 | 持仓、成本、可用资金、已实现盈亏 | 券商页核对 | 每次变动后 | 组合与风险 |

### 3.1 数据状态规则

- 每一项数据都带来源、采集时间、实时/收盘/估算状态。
- 盘中现价与盘口超过约 5 分钟、筹码快照超过一个交易日，必须提示降级。
- 未取得原始筹码数值时只能标记“估算”或“缺失”，不可填入推断值。
- 数据缺失的默认动作是“禁止试错”，而不是补写主观结论。

### 3.2 数据来源优先级

不要求所有数据都从东财网站获取。按“事实来源、速度、可复现性”选择来源，避免浏览器采集成为单点瓶颈：

| 数据 | 首选来源 | 备用来源 | 原因 |
|---|---|---|---|
| 历史日线、技术指标、回测 | 本地 MySQL | 已落库历史数据 | 本地计算最快、可重复、无页面波动 |
| 持仓、可用资金、已实现盈亏 | 券商持仓/资金页核对 | 本地已确认快照 | 券商是账户事实真源 |
| 公告、停复牌、监管、业绩风险 | 交易所/公司正式披露 | 东财公告聚合页 | 风险事项优先正式披露，聚合页用于发现 |
| 盘中现价、分时、量比、换手、资金、板块、筹码、盘口 | 东财页面 OpenCLI 快照 | 最近有效快照（仅展示，不能通过门禁） | 需要浏览器会话下的页面数据与瞬时证据 |
| 行业/概念成员 | 本地参考缓存 | 东财板块页刷新 | 不应在每次盘中诊断重复抓取 |
| 市场状态输入 | 已核验的指数、广度、成交额快照 | 无 | 缺任一核心市场字段时输出“风险冻结” |

OpenCLI 是盘中东财页面采集的标准适配器，但不是所有数据的最快或最高质量来源；对历史计算和账户事实，直接读取本地/券商核对更快且更可靠。

### 3.2.1 MySQL 日线增量更新契约

MySQL 是可更新的本地日线事实库，不能把“库中已有历史”误当成“数据已就绪”。每次收盘计划、回测或技术指标计算前均先执行 `daily-bar-sync` 检查；更新操作必须幂等、可审计，且不能把盘中未收盘 K 线写入历史表。

| 范围 | 触发条件 | 更新动作 | 成功条件 | 失败动作 |
|---|---|---|---|---|
| 关键标的 | P0/P1、持仓或用户指定代码的最新日线缺失/落后 | 单 OpenCLI 会话顺序批量读取最近 120 根日 K，按 `code + trade_date` upsert | 目标交易日存在，OHLCV 完整，最新 3 个交易日无缺口 | 不生成该股新价格计划；持仓只展示旧计划已过期 |
| 全市场选股库 | 全市场最新交易日缺失、行数异常或批量更新任务未成功 | 仅通过可用的结构化日线数据源批量更新；未来可替换为付费数据适配器 | 目标交易日覆盖率达到配置阈值，数据审计通过 | 当日不运行全市场新选股，只允许管理已有持仓 |
| 修订窗口 | 每个收盘更新后 | 回刷最近 3 个交易日并 upsert，覆盖复权/更正/迟到记录 | 无重复主键，OHLCV 与交易日校验通过 | 记录异常，不覆盖上次已验证记录 |

关键标的更新可在免费条件下使用已有 OpenCLI 日 K 能力；全市场数千只股票不能依赖逐页网页采集，必须保留为“已有库数据”或等待结构化数据源可用。更新任务写入 `stt_daily_sync_runs`，至少记录范围、目标日期、来源、代码数、成功/失败数、覆盖率、耗时、原始证据与写入版本。

### 3.2.2 MVP 数据源矩阵（冻结）

第一阶段不接入免费 Tushare API，也不以任何网页逐只补齐全市场日线。每个字段只有一个可放行的主源；备用源只能补齐或交叉核验，不能在字段定义不同的情况下静默替换。

| 数据域 | MVP 主源 | 备用/恢复源 | 放行条件 | 缺失动作 |
|---|---|---|---|---|
| P0/P1、持仓的历史日线 | MySQL `stock_daily` | OpenCLI 日 K 批量补齐 | 目标交易日 + 最近 3 日 OHLCV 完整 | 该股无新计划 |
| 全市场历史日线 | 已通过审计的 MySQL 全市场库 | 无 | 目标日覆盖率达到配置阈值 | 停止全市场选股 |
| 公告、停复牌、监管风险 | 交易所/巨潮正式披露 | 东财仅作发现页 | 标题、时间、链接可追溯 | 风险门禁不通过 |
| 现价、量比、换手、分时、资金 | 东财 OpenCLI 行情/资金页 | 最近有效快照仅展示 | 字段满足 TTL 与代码校验 | 量价门禁不通过 |
| 板块强度与成员 | 东财 OpenCLI 板块页 + 本地成员缓存 | 无 | 板块快照在 15 分钟内 | 板块门禁不通过 |
| 买五卖五与真实成交 | 东财 OpenCLI 盘口页 | 无 | 连续 3 个有效快照 | 盘口门禁不通过 |
| 筹码成本区 | 东财 OpenCLI 收盘快照 | 无 | 页面日期为最近交易日 | 筹码门禁不通过 |
| 账户与可用资金 | 券商页人工核对后写入私有适配层 | 上次已确认值仅展示 | 用户确认时间可追溯 | 风控不放行新开仓 |

任何未来付费或结构化数据源以适配器形式接入，必须先跑 30 个交易日的字段对账和覆盖率报告，才可成为主源；不直接改动诊断或风控规则。

### 3.3 OpenCLI SOP 的两条路径

将现有东财采集拆为快路径与深路径，二者不可混用：

| 路径 | 使用时机 | 标的范围 | 目标耗时 | 必采内容 | 禁止内容 |
|---|---|---:|---:|---|---|
| `fast-check` | 盘中信号验证 | P0 + 已就绪 P1，最多 4 只 | 30–90 秒/只 | 现价、分时量价、板块、资金、盘口、数据时间 | F10 深读、全市场逐页扫描、长文本分析 |
| `eod-warmup` | 收盘后计划 | 活跃持仓 + 次日候选 | 1–3 分钟/只 | 筹码、公告风险、资金摘要、板块归属、收盘快照 | 每只都做长篇深度研究 |
| `deep-research` | 用户明确追问基本面或题材逻辑 | 单只 | 不设交易窗口 SLA | F10、公告链、财务、行业资料 | 作为盘中下单前置条件 |

### 3.4 SOP 优化原则

1. 先读本地缓存，只为过期的快变量请求 OpenCLI。
2. 同一交易时段复用浏览器会话、板块页和已解析字段，不为每只股票重复导航。
3. 先采 P0/P1；抓取超时、页面拦截或字段缺失即写入失败状态，不无限重试。
4. 快路径只返回结构化字段和证据时间；页面原文、截图和深度解释留给 `deep-research`。
5. 对筹码、盘口、资金等页面字段建立页面版本与解析测试；页面结构变化时降级为“未验证”，不得静默使用错误字段。

### 3.5 东财网页采集可靠性协议

东财网页是盘中快变量的浏览器适配来源，不应成为诊断模块的实时依赖。目标不是承诺每次页面都成功，而是在页面波动、登录状态变化或选择器改版时，快速产出**可解释的失败状态**，绝不把错误或旧数据当作交易证据。

1. **单生产者会话**：一个 `OpenCLI` 会话按队列串行采集；本地计算可并行，但不得多个任务同时驱动同一浏览器。每轮开始先做会话健康检查，结束统一释放标签与 lease。
2. **按页面而非按个股组织任务**：行情页一次提取报价、量比、换手与盘口；板块页按题材共享；筹码、公告和归属只在收盘预热。禁止一只股票反复跳转多个页面，也不对全市场做逐页深抓。
3. **语义就绪与身份校验**：等待目标字段或页面状态，而非只固定 sleep；每次写入前必须验证证券代码、交易日、页面时间、单位和数值范围。代码不匹配、上一页残留、空壳 DOM 一律丢弃并记为失败。
4. **字段级恢复**：可恢复错误（`stale page`、`detached`、短时加载超时）最多重试 2 次，间隔 1 秒、2 秒；先重取缺失页面，不能因资金页失败重做已验证的行情页。代码不匹配或解析错误不重试同一 DOM，改为清理会话后重新导航一次。
5. **缓存优先和熔断**：成功快照立即原子落库；仅缺失或过期字段进入队列。单字段连续两次失败即停止该轮重试；同一页面类型在 10 分钟窗口失败率超过 30% 时熔断，后续任务直接使用“数据不可用”结果，等待下一次健康探针恢复。
6. **失败可观测**：每次抓取都记录页面类型、代码、耗时、重试次数、错误类别、字段完整率、解析器版本、原始证据引用与时间。对话层只读取已提交快照，不能自行发起隐式页面重试。
7. **安全降级**：旧快照只能展示“上次有效值 + 时间”，不能让任何门禁通过；关键快变量缺失时固定输出 `NO_TRADE` 或市场 `FREEZE`。

建议先用 50 次独立采集作为上线验收样本：`quote` 成功率不低于 95%，`sector` 与 `order_book` 不低于 90%，关键字段完整率不低于 95%，且代码身份错配必须为 0。未达标时先修复页面适配或缩小抓取范围，不增加交易频率。

## 4. 市场环境引擎

市场环境是所有新开仓的一级门禁，输出 `允许试错 / 限制交易 / 风险冻结`。

### 输入

- 指数趋势、全市场涨跌比、成交额变化。
- 主线板块数量、强势股与亏钱效应。
- 高位股反馈、跌停/炸板情况与题材持续性。

### 输出

```text
市场状态：允许试错 / 限制交易 / 风险冻结
允许题材：……
禁止追逐：……
候选最大数量：N
```

市场环境不负责挑个股，但能阻止在亏钱效应、流动性收缩或题材退潮时开新仓。

## 5. 短线选股引擎（阶段 D 目标能力）

### 5.1 职责

在阶段 D 启用后，收盘后从全市场生成不超过 3–5 只研究候选。选股输出是研究任务，不是买入建议；MVP 期间候选只能由用户指定自选、既有持仓或手动维护的 P1 观察池进入，系统不自动扫描全市场。

### 5.2 候选门槛

1. 有可验证的题材、公告、订单或行业催化，排除纯传闻。
2. 所属板块存在共振，不依赖单只异动。
3. 量价趋势满足突破、回踩或分歧转强的基础结构。
4. 流动性足够，单日急涨、高位不可成交或风险公告的标的排除。
5. 不与现有持仓重复，不突破主题敞口和交易名额。

### 5.3 候选输出契约

```text
代码 / 名称：
候选类型：突破启动 / 回踩观察 / 分歧转强
入选证据：题材、板块、量价、资金、风险各一条
数据时间：
待诊断缺口：筹码 / 盘口 / 公告 / 其他
状态：收盘候选，禁止直接买入
```

选股引擎不输出“推荐买入”“目标价”或自动仓位。

## 6. 短线个股诊断引擎

### 6.1 职责

对候选和现有持仓生成统一的价格计划。收盘后产出次日计划；盘中只验证是否触发，不临时改变规则。

### 6.2 八项输入

| 类别 | 必填字段 |
|---|---|
| 题材与催化 | 催化标题与时间、题材归属、公告/监管/减持风险 |
| 板块共振 | 板块涨幅、上涨/强势家数、领涨股持续性、相对强度 |
| 量价与资金 | 分时量能、换手、量比、VWAP、主力流入与连续性 |
| 筹码位置 | 90% 成本上下限、平均成本、获利比例、集中度 |
| 盘口承接 | 买五卖五总量、真实成交消化、撤单与回踩承接 |
| 大盘环境 | 指数广度、成交额、风险偏好 |
| 竞价与可执行性 | 竞价涨跌、开盘跳空、流动性与涨跌停限制 |
| 风险与退出 | 公告风险、失效价、最大持有期、退出路径 |

### 6.3 技术指标与价格位

| 指标 | 用途 |
|---|---|
| MA5 / MA10 / MA20 | 趋势方向、回踩观察区 |
| 近 20 日高低点、前高前低 | 压力位、支撑位与突破确认 |
| ATR14 | 价格容差、止损距离与波动适配 |
| VWAP | 盘中强弱与回踩承接 |
| 90% 成本上下限 | 筹码支撑、套牢压力与压力位校验 |
| 平均成本、获利比例、集中度 | 判断获利盘与筹码稳定性 |
| 量比、换手、成交额、资金流 | 区分放量突破、缩量回踩与资金退潮 |

### 6.4 价格计划输出

```text
结论：禁止试错 / 仅观察 / 可人工试错 / 减仓退出
数据状态：交易日、采集时间、实时或收盘、数据缺口
突破触发价：关键压力位被有效突破后的价格
回踩观察区：关键支撑 ± 0.25 ATR
硬失效价：筹码下限、前低或趋势支撑失守的价格
第一减仓参考：入场价 + 2R（R = 入场价 - 硬失效价）
最大试错股数：由 500 元风险预算反推，按 100 股取整
```

压力位从近 20 日高点、前高与 90% 成本上限中选取最相关的一档；支撑分为观察支撑和硬失效支撑。所有具体价格必须注明计算依据和数据时间。

### 6.5 四种结论

| 结论 | 条件 | 动作 |
|---|---|---|
| 禁止试错 | 核心数据缺失、风险公告、环境冻结、价格不在计划区 | 不交易 |
| 仅观察 | 趋势存在，但五项确认不足 | 记录，不下单 |
| 可人工试错 | 五项核心确认通过，环境/竞价/风险门禁正常，风控允许 | 用户自行决定是否小仓 |
| 减仓退出 | 硬失效价触发，或板块退潮、资金转弱、承接失败 | 按预案降低风险 |

## 7. 组合与风控引擎

### 7.1 否决顺序

1. 市场状态是否允许新开仓？
2. 是否仍有交易名额和总仓位空间？
3. 新候选是否与已有主题、行业或波动来源高度重复？
4. 入场价到硬失效价的风险是否可用 500 元预算覆盖？
5. 股票是否具备可成交、可退出的流动性？

任何一项不通过，最终结论为“禁止试错”。

### 7.2 仓位计算

```text
每股风险 = 计划入场价 - 硬失效价
风险允许股数 = floor(500 / 每股风险 / 100) × 100
金额上限股数 = floor(单票金额上限 / 计划入场价 / 100) × 100
最终可试错股数 = min(风险允许股数, 金额上限股数, 剩余总暴露允许股数)
```

若硬失效价不低于入场价、风险允许股数小于 100 股或退出流动性不足，则不生成交易计划。

### 7.3 固定风控输出

```text
账户状态：允许试错 / 限制交易 / 风险冻结
可开交易名额：N
剩余交易预算：¥X
禁止新增主题：……
候选最终状态：禁止 / 观察 / 可人工试错
```

## 8. 日内工作流

### 8.1 收盘后（阶段 D 完整流程）

1. 刷新日线、账户和持仓快照。
2. 运行市场环境与短线选股，得到候选池。
3. 对候选与持仓运行个股诊断，生成次日价格计划。
4. 运行组合与风控，写入可交易名额、主题限制与最大股数。
5. Agent 对话按固定交易决策卡输出计划与数据缺口。

MVP 收盘流程替换第 2 步：不运行全市场选股，只读取用户指定或已维护的 P1 观察池（最多 5 只），再执行个股诊断、风控与冻结计划。

### 8.2 盘中

1. 仅刷新已建档候选与现有持仓，不临时扩展交易范围。
2. 采集现价、分时、资金、板块和盘口快照。
3. 对照昨晚计划输出“未触发 / 禁止 / 观察 / 可人工试错 / 退出”。
4. 用户自行决定是否下单；系统只记录决定与结果。

### 8.3 收盘复盘

记录信号是否触发、是否执行、实际成交、滑点、退出原因及 1/3/5 日表现。计划外交易必须单列，不能与策略交易混算。

## 9. 日志、前向验证与回测

### 9.1 必须保存的记录

- 候选出现时的八项数据快照与时间戳。
- 收盘价格计划和盘中确认结果。
- 用户实际成交、计划风险、实际盈亏、持有天数。
- 未执行信号的后续表现，防止只看已成交样本。

### 9.2 验证原则

- 日线回测只能验证技术候选层，不能伪造题材、筹码与盘口数据。
- 五项确认必须通过前向模拟交易记录验证。
- 参数选择在历史训练期完成后，必须在独立样本外期间验证。
- 不因单一阶段亏损而持续调参；先判断市场环境和数据缺口。

## 10. Agent 对话意图路由与输出

交易系统不强制每次输出固定卡片。固定的是数据契约、主信号和价格计划；Agent 根据用户当次问题选择最小必要输出，避免无关信息干扰交易判断。

| 用户意图 | 默认输出 | 必含内容 |
|---|---|---|
| “今天该做什么” / “账户风险” | 每日总览 | 市场状态、账户状态、必须处理项、可开名额、禁止主题 |
| “分析 XXX” / “盘中怎么看” | 单股交易决策卡 | 主信号、唯一下一步、关键价格、最大股数、数据时间、失败门禁 |
| “选什么” / “收盘选股” | 候选列表 | 候选证据、淘汰原因、待补诊断项；不输出买入指令 |
| “我的持仓怎么办” | 持仓风险摘要 + 指定股票决策卡 | 组合集中度、优先级、每只需处理动作 |
| “复盘” / “策略有效吗” | 计划—实际对照报告 | T 日计划、T+1 结果、执行偏差、分组统计 |
| “查一个指标” | 原始数据回答 | 数值、来源、时间、是否足以通过对应门禁 |

若用户未说明范围，Agent 只追问或默认输出“每日总览”；不自动附带候选、持仓和复盘全文。

### 10.1 单股交易决策卡

- 仅在用户询问指定股票、盘中触发或持仓操作时输出。
- 包含结论、关键失效价、交易预算权重、数据新鲜度，以及按需展开的八项确认、支撑压力和退出路径。

### 10.2 其他输出的最小化原则

- 候选列表只负责“为何进入研究池”，不混入持仓建议。
- 账户风险摘要只指出系统级限制，不重复每只股票的技术分析。
- 复盘只比较冻结计划与实际结果，不重写当时的交易建议。

## 11. 实施路线

### 阶段 A：统一契约

1. 定义候选、八项快照、价格计划、风控决定、交易日志五类结构化数据。
2. 冻结并实现 [`短线交易规则基线v1.md`](短线交易规则基线v1.md) 的门禁、价格公式和数据降级规则。
3. 将现有个股诊断 Skill 改为只输出统一契约，不再输出散乱文字结论。
4. 将 Agent 对话输出接入结构化状态与数据时间。

阶段 A 的 MVP 范围固定为：**现有持仓 + 用户指定自选 + 最多 5 只 P1 候选**。不开发全市场扫描，不输出自动候选，也不因数据不足改变交易门禁。

### 阶段 B：收盘计划引擎

1. 先使用本地日线计算 MA、ATR、支撑、压力、入场/失效/减仓参考价。
2. 接入筹码收盘快照与公告风险。
3. 对现有持仓和候选生成可复核的次日计划。

### 阶段 C：盘中确认引擎

1. 接入东财行情、板块、资金与盘口快照。
2. 仅做计划触发判定，不临时推荐新标的。
3. 记录数据新鲜度、确认理由和未通过原因。

### 阶段 D：选股与前向验证

阶段 D 的前置条件是：全市场日线库连续 20 个交易日覆盖率达阈值、日线更新有独立审计记录，且不依赖逐页网页补数。未满足时，本阶段不启动。

1. 收紧短线选股为候选层，隔离历史遗留的泛选股逻辑。
2. 用 20–30 笔模拟记录验证五项确认的有效性。
3. 形成周度复盘和规则淘汰机制后，再讨论扩大仓位或自动提醒。

## 12. 验收标准

系统达到以下标准才进入常态使用：

1. 任一候选均能说明来源、时间、题材证据、数据缺口与禁止买入原因。
2. 任一个股诊断均能生成支撑、压力、触发价、失效价、减仓价和最大试错股数，或明确说明为何不能生成。
3. 任一次“可人工试错”均能追溯五项确认、环境门禁和风险计算。
4. 任一持仓均能说明组合角色、主题暴露、退出条件与最长持有期。
5. 周度复盘能区分策略表现、执行偏差和计划外交易。
6. 连续 50 次独立采集达到 `quote ≥95%`、`sector/order_book ≥90%`、关键字段完整率 ≥95%、代码身份错配为 0；未达到则只允许离线计划，不开放盘中 `BUY_ALLOWED`。

## 13. 执行时间预算与超时降级

系统不以“数据越多越好”为目标，而以交易窗口内能给出可复核结论为目标。每个模块均须声明目标耗时、超时动作和数据新鲜度。

### 13.1 收盘后流水线

| 顺序 | 模块 | 目标耗时 | 输入范围 | 超时/失败处理 |
|---|---|---:|---|---|
| 1 | 日线与账户刷新 | 2–5 分钟 | 全账户、全市场日线 | 标记数据日期，停止生成新计划 |
| 2 | 市场环境 | 1–2 分钟 | 指数、广度、成交额、主线 | 输出“限制交易”，不等待补数 |
| 3 | P1 候选输入 / 阶段 D 短线选股 | MVP <1 分钟；阶段 D 2–4 分钟 | MVP：手动 P1 池；阶段 D：全市场 → 3–5 只 | MVP 不自动补候选；阶段 D 无合格候选即结束 |
| 4 | 候选诊断 | 1–3 分钟/只 | 最多 3 只优先候选 | 缺筹码/公告/盘口时标记禁止试错 |
| 5 | 持仓计划更新 | 30–90 秒/只 | 最多 3 只活跃交易持仓或触发风险的库存 | 未更新的旧计划标记过期 |
| 6 | 风控汇总与发布 | 1 分钟 | 候选、持仓、账户 | 任一风险数据异常则收紧状态 |

常态目标为收盘后 **20–30 分钟内**完成；首次建档或东财页面异常时可延长，但不得为了赶时效而编造缺失数据。

### 13.2 盘中流水线

盘中只处理“已有收盘计划的候选 + 活跃交易股”，单次优先级不超过 4 只。

| 时间窗 | 工作 | 目标总耗时 | 输出 |
|---|---|---:|---|
| 09:25–09:40 | 竞价、跳空、可成交性 | 3–5 分钟 | 开盘禁止/观察名单 |
| 09:40–10:30 | 首次价格触发与板块、资金、盘口确认 | 5–10 分钟 | 未触发/观察/可人工试错/退出 |
| 14:30–收盘 | 收盘质量与隔夜资格 | 3–6 分钟 | 保留或撤销次日计划 |

单只盘中复核目标为 **30–90 秒**；行情/盘口快照超过 5 分钟或获取超过 3 分钟未完成，结论降级为“数据过期，禁止试错”。

### 13.3 资源控制原则

- 选股负责缩小范围，深度数据只抓候选和活跃持仓，不扫描全市场。
- 本地计算可并行；OpenCLI 页面采集在单一会话中串行批量执行，避免并发抢占浏览器状态；风控汇总必须在所有计划后串行执行。
- 盘中不做完整基本面研究；公告与风险排雷优先于新增技术指标。
- Agent 对话只读取已生成的计划与快照；页面采集与展示层不属于第一阶段范围。

## 14. 可拆分与可分享的模块设计

### 14.1 模块清单

| 模块 | 独立职责 | 最小输入 | 标准输出 | 不应依赖 |
|---|---|---|---|---|
| `market-regime` | 判定市场可交易状态 | 指数、广度、成交额、情绪统计 | 市场状态与限制 | 个股持仓、券商信息 |
| `short-term-selection` | 全市场生成研究候选 | 日线、主题/公告、流动性 | 候选列表与证据 | 用户成本、下单权限 |
| `single-stock-trade-plan` | 生成个股价格计划 | 日线、筹码、资金、公告、盘口快照 | 支撑/压力/触发/失效/减仓计划 | 组合仓位决策 |
| `portfolio-risk` | 计算仓位与最终否决 | 账户、持仓、交易计划、主题映射 | 允许状态、最大股数、限制 | 东财页面细节 |
| `intraday-verifier` | 盘中对照计划验证 | 已冻结计划、实时快照 | 未触发/观察/可人工试错/退出 | 重新选股 |
| `trade-review` | 评估计划与执行效果 | 计划、快照、成交与后续价格 | 复盘统计与淘汰建议 | 实时页面控制 |

### 14.2 统一数据契约

所有模块只通过版本化 JSON 对象通信，不读取彼此的内部文件：

```text
MarketStateV1        市场状态与允许限制
CandidateV1          收盘候选与入选证据
EvidenceSnapshotV1   八项数据、来源、时间戳、新鲜度
TradePlanV1          价格位、触发条件、风险距离、有效期
RiskDecisionV1       交易名额、最大股数、主题/回撤否决原因
IntradayDecisionV1   盘中快照与触发结论
TradeJournalV1       计划、用户执行、结果与复盘标签
```

每个对象必须含 `schema_version`、`as_of`、`source`、`data_status` 和 `code`（市场对象除外）。缺少这些字段的对象不得进入下游模块。

```text
a-share-short-term-trading/

```

Skill 是调用规范，交易引擎是可测试代码；两者分离，避免把业务逻辑写进提示词。

### 14.4 可分享边界

可以独立分享：

- 数据契约、技术价格计算、风险仓位计算、候选过滤、盘中验证逻辑。
- 脱敏样例数据、单元测试、回测与前向验证脚本。
- Skill 的工作流、数据缺失规则与输出模板。

不得进入可分享模块：

- 券商账号、登录会话、持仓明细、成本、资金流水、个人风险偏好。
- `.env`、OpenCLI Profile、浏览器 Cookie、第三方密钥。
- 个人执行卡和个人交易日志原始内容。

个人配置应作为独立的本地适配层，通过 `PortfolioProfile` 注入 `portfolio-risk`，并保持在忽略列表中。这样同一模块可被不同用户复用，而不会暴露账户信息。

### 14.5 模块验收要求

每个模块在独立运行时必须具备：

1. 一个明确的 CLI 或 Python 函数入口。
2. 输入 JSON Schema 校验和至少一个脱敏 fixture。
3. 可重复运行的单元测试。
4. 目标耗时、超时降级状态和错误信息。
5. 不依赖券商会话即可完成离线测试。

## 15. 指标预热、缓存与刷新策略

指标获取按变化速度分层。原则是：**慢变量提前固化，快变量按优先级刷新，任何过期数据都不能伪装成实时证据。**

### 15.1 指标变化分层

| 数据层 | 典型指标 | 变化频率 | 缓存有效期 | 获取策略 |
|---|---|---|---|---|
| 静态参考 | 股票代码、申万/东财行业归属、主营标签、交易规则、流通股本 | 公告、指数或分类调整时 | 7–30 天 | 建档或夜间刷新 |
| 半静态归属 | 概念板块成员关系 | 新增概念、成分调整时 | 1–7 天 | 收盘后或周度刷新 |
| 低频事实 | 财报、主营、股东、监管/减持、历史公告 | 披露时 | 至下一次披露 | 收盘后预热，事件触发刷新 |
| 收盘指标 | 日线、MA、ATR、20 日高低点、90% 成本区、平均成本、获利比例、集中度、5 日资金 | 每交易日 | 当日收盘至下一交易日收盘 | 收盘后批量计算/采集 |
| 盘中慢变量 | 板块归属、题材热度、板块梯队、候选交易计划 | 10–30 分钟 | 10–30 分钟 | 盘中按观察窗口刷新 |
| 盘中快变量 | 现价、涨跌幅、分时量能、换手、量比、VWAP、主力流、买五卖五 | 秒至分钟 | 1–5 分钟 | 仅对优先标的按需抓取 |

筹码分布属于“收盘指标”：取得 90% 成本上下限、平均成本、获利比例和集中度后，应保留原始来源和日期，次日盘中可直接引用；只有隔夜/收盘后更新，不需要为每次盘中复核重复采集。

板块信息必须拆成三层：`行业归属` 是静态参考；`概念成员关系` 是半静态参考；`交易题材状态`（当日主线、板块涨幅、梯队、领涨股、资金与持续性）是盘中慢变量，必须按观察窗口刷新，不能用静态行业标签替代。

### 15.2 标的优先级

不对全市场做深度预热，而是维护一个有上限的“热标的池”：

| 优先级 | 标的范围 | 预热内容 | 盘中刷新 |
|---|---|---|---|
| P0 | 活跃交易持仓，最多 3 只 | 全部八项、价格计划、风险状态 | 每个观察窗口；接近触发价时优先 |
| P1 | 次日候选，最多 5 只 | 全部收盘指标、筹码、公告、板块与价格计划 | 竞价、首次触发、尾盘 |
| P2 | 自选观察，最多 20 只 | 日线技术、公告风险、行业映射、收盘筹码 | 收盘后；盘中不主动抓盘口 |
| P3 | 全市场 | 日线、流动性、基础选股字段 | 仅收盘选股阶段 |

P0/P1 总数必须受交易名额和人工复核能力限制；P2 不进入盘中抓取队列，除非被选股引擎升级为 P1。

### 15.3 预热时间线

```text
收盘后：刷新日线 → 计算技术价位 → 预热 P0/P1 的公告、筹码与资金 → 生成次日计划
盘前：检查 P0/P1 隔夜公告与风险事件 → 固化待验证计划
09:25：刷新 P0/P1 竞价、跳空、可成交性
09:40–10:30：仅刷新接近计划触发价或已持仓的 P0/P1
14:30：刷新 P0/P1 板块、资金、盘口与收盘质量
收盘：写入快照、触发记录与复盘队列
```

其中“刷新日线”固定为两步：先检查 MySQL 的目标交易日、覆盖率和关键代码缺口；仅缺失的 P0/P1 进入 OpenCLI 批量补齐队列，成功 upsert 后才重新计算 MA/ATR/支撑压力。全市场库未就绪时停止新一轮全市场选股，不以旧日线生成当日候选。

触发式刷新优先于轮询：当现价距突破价、回踩区或失效价不超过 `0.5 ATR` 时，将对应股票提升到 P0，并刷新盘口、资金和板块；未接近任何价格位的 P1 标的只保留低频快照。

### 15.4 缓存对象与证据保留

每条缓存采用“原始证据 + 解析字段 + 新鲜度”三层存储：

```text
CacheKey: {code}:{data_kind}:{trading_date}:{snapshot_time}
RawEvidence: 页面文本/截图引用/原始结构化响应
ParsedData: 指标字段与单位
Freshness: as_of, ttl_seconds, source, data_status
```

关键对象：

- `daily_technical_snapshot`：MA、ATR、前高前低、支撑压力。
- `chip_snapshot`：90% 成本上下限、平均成本、获利比例、集中度及页面日期。
- `event_risk_snapshot`：公告、监管、减持、业绩与停复牌风险。
- `sector_snapshot`：板块排名、强势家数、领涨股、题材状态。
- `quote_snapshot`：现价、成交额、换手、量比、VWAP、资金字段。
- `order_book_snapshot`：买卖五、委买委卖、真实成交观察与采集时间。

同一数据不覆盖历史快照；新快照追加，交易计划只引用对应 `as_of` 的证据，便于事后验证。

### 15.5 刷新队列与降级规则

1. 先读取缓存；未过期则直接复用，并向用户展示原始时间。
2. 缓存缺失或过期时，将任务放入 P0 → P1 → P2 队列；每轮只处理允许数量。
3. OpenCLI 页面获取失败时，保留上次有效快照但标为过期；不以旧值通过交易门禁。
4. 盘口和实时行情超过 5 分钟、板块/资金超过 15 分钟、筹码超过一个交易日，相关确认项自动“不通过”。
5. 任何关键项连续两次获取失败，停止重复抓取并把诊断状态降为“数据缺失，禁止试错”，等待人工重试。

### 15.6 采集任务、熔断与健康探针

`data-cache` 将一次页面采集拆成独立任务：`market`、`quote`、`sector`、`fund_flow`、`order_book`、`chip`。任务只负责获取、校验、写入快照；诊断和风控只读成功提交的快照。

```text
任务入队 → 复用单会话 → 语义等待 → 代码/时间/单位校验 → 原子写快照
   ├─ 可恢复页面错误：字段级重试 1 秒、2 秒，最多 2 次
   ├─ 代码错配/解析错误：清理会话并重新导航 1 次
   └─ 两次失败或页面类型熔断：写失败证据 → 降级为 NO_TRADE/FREEZE
```

- 健康探针：开盘前与收盘后各运行一次，检查主板、科创板和市场页的可达性、代码校验与最小字段；探针失败时不启动盘中快路径。
- 页面类型熔断：同类页面在 10 分钟内失败率超过 30% 时停止新请求 10 分钟；恢复后先由健康探针放行，避免大量任务反复撞页面。
- 指标：按页面类型统计成功率、字段完整率、身份错配率、`p50/p95` 耗时、重试率、解析错误率、旧缓存服务次数与熔断次数；这些指标是采集层周度复盘的固定输入。
- 回放：每个解析器保留脱敏 HTML/文本 fixture 和期望字段；页面改版或错误率异常时，先用 fixture 复现并修复，再恢复自动采集。

### 15.7 模块化实现边界

新增 `data-cache` 适配层，向选股、诊断和盘中验证提供相同的只读快照接口；业务模块不得自行访问浏览器页面。

```text
data-cache
├── warmup_scheduler    # 按 P0–P3 和时间窗创建任务
├── source_adapters     # MySQL、OpenCLI、券商核对的适配器
├── snapshot_store      # 原始证据、解析字段、版本与 TTL
└── freshness_policy    # 过期、降级与重试规则
```

这样 `single-stock-trade-plan` 在收盘后读稳定快照，`intraday-verifier` 只请求快变量，`portfolio-risk` 只消费最终计划与账户事实；三者均可独立测试和分享。

### 15.8 `daily-bar-sync` CLI 与输出契约（冻结）

第一版只实现 `critical` 范围，调用方必须显式给出代码列表；`universe` 只做检查，不得偷偷通过 OpenCLI 对全市场逐页回填。

```bash
daily-bar-sync \
  --scope critical \
  --codes 600000,688001 \
  --target-date auto \
  --lookback-bars 120 \
  --repair-days 3 \
  --source-policy mysql_then_opencli \
  --output json
```

| 参数 | 固定语义 |
|---|---|
| `--scope` | `critical` 或 `universe`；MVP 仅 `critical` 允许写入 |
| `--codes` | `critical` 必填，去重后最多 8 只；超过上限直接失败，不截断 |
| `--target-date` | `auto` 或明确交易日；`auto` 只能选择已收盘且经交易日历确认的最近交易日 |
| `--lookback-bars` | 默认 120，最小 60；用于补齐技术计算所需窗口 |
| `--repair-days` | 默认 3；回刷最近交易日并幂等 upsert |
| `--source-policy` | MVP 固定 `mysql_then_opencli`，禁止使用未登记数据源 |
| `--dry-run` | 仅输出缺口、计划任务与预期写入，不访问页面或写库 |

标准 JSON 输出必须包含：`run_id`、`scope`、`target_trade_date`、`source_policy`、`status`（`READY` / `UPDATED` / `PARTIAL` / `FAILED`）、`requested_codes`、`ready_codes`、`failed_codes`、`coverage_ratio`、`missing_dates`、`upserted_rows`、`started_at`、`finished_at`、`evidence_refs` 与 `failure_reasons`。`PARTIAL` 和 `FAILED` 均不得被价格计划引擎视为可用。

MVP 验收为：8 只以内关键标的可重复执行、重复执行不产生重复日线；成功代码仅在目标日和最近 3 日校验都通过后返回 `READY` 或 `UPDATED`；任一失败代码保留在输出中且可追溯到采集证据。全市场检查只输出覆盖率与缺口，不产生补数请求。

## 16. 现状与下一步

当前已具备账户操作台、持仓执行卡、收盘候选、基础日线回测，以及八项确认卡的展示框架；缺少的是统一数据契约、实际筹码/盘口快照采集和“指标 → 价格 → 动作”的诊断引擎。

下一步只做阶段 A：先冻结数据模型与输出格式，再实现收盘计划引擎。没有统一契约前，不继续增加选股指标或盘中自动化。

## 17. T 日决策与 T+1 实际结果对照闭环

必须建立该闭环。它不是为了事后证明观点正确，而是用来区分“规则本身无效”“计划有效但执行偏差”“市场环境不匹配”三类问题，并为后续概率预测提供无未来数据的训练样本。

### 17.1 时间边界

| 记录 | 写入时点 | 允许包含的数据 | 禁止包含的数据 |
|---|---|---|---|
| `DecisionSnapshotV1` | T 日收盘计划生成时 | 截至 T 日收盘的指标、证据、价格计划、风险决定 | T+1 的竞价、价格、新闻和结果 |
| `OutcomeObservationV1` | T+1 盘中/收盘及后续 | 竞价、开高低收、触发情况、盘口/资金快照、用户实际执行 | 修改 T 日原计划 |
| `PlanEvaluationV1` | T+1 收盘、T+3、T+5 | 计划与实际对照、结果标签、复盘结论 | 用结果覆盖原始证据 |

T 日计划写入后不可更新，只能创建新版本并注明 `supersedes_decision_id`。这样回测、前向验证和复盘才能确认当时真正看到了什么。

### 17.2 计划生命周期

```text
CandidateV1
  → TradePlanV1（草案）
  → RiskDecisionV1（允许/否决）
  → DecisionSnapshotV1（T 日冻结）
  → IntradayDecisionV1（T+1 观察，不改原计划）
  → OutcomeObservationV1（T+1/T+3/T+5 实际）
  → PlanEvaluationV1（复盘标签）
```

只有 `DecisionSnapshotV1` 已冻结且未过期的标的能进入盘中验证；未完成风控或市场状态冻结的候选在 T+1 只能记录结果，不生成交易动作。

### 17.3 T 日决策快照

```text
decision_id / code / decision_at / trading_date / schema_version
market_state / candidate_reason / evidence_snapshot_ids
support_zone / resistance_price / trigger_price / invalidation_price / take_profit_reference
planned_position_limit / risk_per_share / max_shares
decision: 禁止试错 / 仅观察 / 可人工试错 / 减仓退出
decision_reasons / data_status / expires_at
```

即使结论是“禁止试错”也必须记录；没有被执行的计划同样是评估规则质量的重要样本。

### 17.4 T+1 实际观察

```text
decision_id / observed_at / observation_window
auction_price / open / high / low / close / volume / turnover
triggered: true/false
trigger_type: 突破 / 回踩 / 失效 / 未触发
five_gate_status: 题材、板块、量价资金、筹码、盘口
market_state_actual / gap_pct / slippage_assumption
user_action: 未执行 / 买入 / 卖出 / 减仓
actual_trade_ref / data_status
```

观察窗口至少包括 `09:25–09:40`、`09:40–10:30`、`14:30–收盘`；有交易计划的标的还要补充 T+3 与 T+5 的结果观察。

### 17.5 对照指标

| 维度 | 指标 | 用途 |
|---|---|---|
| 价格计划 | 是否触发、触发时刻、开盘跳空、计划价与实际成交偏差 | 检查价格位是否可执行 |
| 风险控制 | 失效价是否触发、最大不利波动、实际滑点 | 检查止损距离和流动性假设 |
| 信号质量 | 触发后 1/3/5 日收益、胜率、盈亏比、触发后最大有利波动 | 判断信号是否有正期望 |
| 五项确认 | 每个确认项通过/不通过时的分组结果 | 淘汰无贡献或噪音指标 |
| 环境适配 | 按市场状态、题材、板块、波动分层统计 | 避免把某一行情阶段误当通用规律 |
| 执行偏差 | 计划内/计划外交易、未执行信号后续表现 | 区分策略问题和人为执行问题 |

### 17.6 后续预测的正确用法

初期不预测具体涨幅或涨停概率，而是基于累积样本输出条件概率，例如：

```text
在“市场允许试错 + 突破触发 + 五项确认全通过 + 风险距离合格”条件下，
历史前向样本的 T+1 / T+3 / T+5 胜率、平均收益、最大不利波动分别为……
```

只有在样本量、跨市场阶段和执行记录都达到基本要求后，才比较不同条件组合的概率；概率输出必须同时展示样本数、时间范围和数据缺口，不能替代风险上限。

### 17.7 存储设计补充

短线系统使用独立的 `stt_` 表前缀（或独立 schema），不修改既有 `stock-ai` 业务表；历史日线和账户核对仅通过适配层读取。

| 表 | 作用 | 主键建议 |
|---|---|---|
| `stt_watchlist` | P0–P3 热标的池、来源与优先级 | `code + watchlist_date` |
| `stt_market_states` | 市场状态、允许主题和限制原因 | `trading_date + as_of` |
| `stt_candidates` | 收盘候选、证据引用和淘汰原因 | `candidate_id` |
| `stt_evidence_snapshots` | 技术、筹码、公告、板块、行情、盘口原始证据与解析字段 | `snapshot_id`；索引 `code + kind + as_of` |
| `stt_capture_attempts` | 每次页面采集的结果、耗时、重试、错误类型、字段完整率和证据引用 | `attempt_id`；索引 `kind + started_at`、`code + started_at` |
| `stt_source_health` | 按时间桶汇总页面成功率、延迟、身份错配、解析错误与熔断状态 | `source + kind + bucket_at` |
| `stt_daily_sync_runs` | 日线检查、补齐、upsert、覆盖率与异常记录 | `run_id`；索引 `target_trade_date + scope` |
| `stt_trade_plans` | 当前有效的支撑、压力、触发、失效与减仓计划 | `plan_id`；索引 `code + status + expires_at` |
| `stt_risk_decisions` | 主题敞口、交易名额、最大股数和否决原因 | `risk_decision_id` |
| `stt_decision_snapshots` | T 日冻结的计划与证据引用 | `decision_id` |
| `stt_intraday_decisions` | 盘中触发与门禁验证结果 | `decision_id + observed_at` |
| `stt_outcome_observations` | T+1 及后续各窗口的实际快照 | `decision_id + observed_at + observation_window` |
| `stt_trade_journal` | 用户实际执行、计划偏差、成交和退出原因 | `journal_id`；关联 `decision_id` |
| `stt_plan_evaluations` | T+1/T+3/T+5 的对照、标签与复盘 | `decision_id + evaluation_horizon` |

`stt_trade_plans` 只保存当前有效计划的索引；评价和统计必须引用冻结的 `stt_decision_snapshots`，不能只读会被更新的当前计划。原始页面文本/截图保留在文件或对象存储，数据库只保存引用、摘要和校验信息，避免 MySQL 膨胀。

## 18. AI 调用边界与离线运行

核心交易链路必须可在完全不调用大模型的情况下运行。数据采集、缓存、技术计算、选股过滤、价格计划、风险否决、盘中触发判定、日志写入和统计评价均使用确定性代码与结构化规则完成。

### 18.1 默认运行模式

```text
AI_MODE=off（默认）
```

在该模式下，系统仍能完成收盘计划、盘中验证、风控与复盘；任何 AI 服务不可用、延迟过高或成本超预算时，不影响交易状态的生成。

### 18.2 AI 仅可承担的辅助工作

| 场景 | AI 可做 | AI 不可做 |
|---|---|---|
| 公告与新闻 | 提炼事件摘要、列出待核验风险 | 把摘要当事实或绕过公告风险门禁 |
| 收盘复盘 | 解释已生成的结构化结果、归纳执行偏差 | 修改 T 日计划或实际结果 |
| 研究迭代 | 根据统计提出待验证的规则假设 | 直接发布新交易规则或调高仓位 |
| 看板文案 | 把结构化状态转为易读说明 | 覆盖价格信号、风控结论或最大股数 |

AI 输出必须标记 `generated_by_ai=true`、模型版本、生成时间和引用的结构化证据；它只能追加说明，不得写入或覆盖 `RiskDecisionV1`、`TradePlanV1`、`IntradayDecisionV1` 的决定字段。

### 18.3 运行降级

1. AI 不可用：只展示结构化价格计划、通过/不通过原因与数据缺口。
2. OpenCLI 不可用：保留有效缓存并标记过期；关键快变量过期则禁止试错。
3. MySQL 不可用：不生成新计划、不进行盘中确认，只显示最近快照的只读状态。

这使项目可部署为低成本、可复核的规则系统；AI 是可插拔的解释层，而非交易引擎的单点依赖。

## 19. 面向散户的最终输出契约

系统的最终输出不是研究报告，而是一张可执行、可核对的交易决策卡。每个标的在同一时刻只能有一个主信号；系统必须明确说明当前动作、下一触发条件、价格和最大风险，不能输出相互矛盾的多条建议。

### 19.1 固定主信号

| 信号代码 | 用户看到的动作 | 系统含义 |
|---|---|---|
| `NO_TRADE` | 禁止交易 | 数据缺失、风控否决、风险事件或条件不成立；不买、不加仓 |
| `WAIT_ENTRY` | 等待触发 | 当前不操作；仅等待写明的突破价/回踩区被满足 |
| `BUY_ALLOWED` | 可人工试错买入 | 五项确认、价格与风控全部通过；显示精确入场区、最大股数与失效价 |
| `HOLD` | 继续持有，不加仓 | 已持仓未触发退出；显示防守价与下一观察点 |
| `REDUCE` | 减仓 | 显示应减股数/比例、执行价格条件与剩余风险 |
| `EXIT` | 退出 | 硬失效、风险事件或计划到期；显示应退出的可用股数与原因 |

`BUY_ALLOWED` 只表示系统条件已满足，用户仍自行提交订单；没有该信号时，界面不得以“偏多”“关注”“强弱”等措辞暗示买入。

### 19.2 决策卡的固定结构

```text

【数据状态】2026-xx-xx 10:02｜实时快照｜行情 1 分钟前｜筹码为上一交易日收盘
【当前核对数据】
现价 / 涨跌幅 / VWAP / 量比 / 换手 / 主力资金

90% 成本下限–上限 / 平均成本 / 获利比例 / 集中度

【价格计划】

【风控计算】
```

所有数字都必须附带来源时间；不可用的数据显示“缺失”，并使对应门禁不通过，不能以“预计”“大概”填充。

### 19.3 收盘版与盘中版

| 场景 | 主输出 | 用户可直接核对的内容 |
|---|---|---|
| 收盘后 | 次日单标的交易计划 | 支撑压力、触发价、失效价、最大股数、五项待验证项 |
| 盘中未触发 | `NO_TRADE` 或 `WAIT_ENTRY` | 实时价距触发价、已通过/未通过门禁、下次检查点 |
| 盘中触发 | `BUY_ALLOWED` / `REDUCE` / `EXIT` | 触发时间、实时价、成交/资金/盘口证据、具体股数 |
| 收盘复盘 | 计划是否触发及偏差 | T 日计划、T+1 实际、执行与 1/3/5 日结果 |

### 19.4 价格与行动的生成规则

1. 系统先计算技术与筹码价格位，再生成主信号；不从自然语言结论反推价格。
2. 一笔新开仓只允许一个入场计划、一个硬失效价和一个最大股数；条件变化时新建计划版本。
3. 已持仓的 `REDUCE`/`EXIT` 必须写入股数或比例，并区分可用股与锁定股。
4. 触发价被价格穿越但五项门禁未全通过时，主信号仍为 `NO_TRADE`，并列出失败门禁代码。
5. 任何主信号的有效期最长到下一个收盘计划更新；过期后自动降为 `NO_TRADE`。

### 19.5 Agent 对话展示

每日总览只展示需要行动的内容：

```text
账户状态：允许试错 / 限制交易 / 风险冻结
当前必须处理：XXX EXIT；XXX WAIT_ENTRY
今日可人工试错：0–N 只
禁止新增主题：……
```

当用户发起单股诊断时，Agent 默认先输出“主信号、唯一下一步、关键价格、最大股数、数据时间”；用户要求时再展开八项原始指标。这样既给出清晰的交易逻辑，也保留足够数据供用户实际核对。
