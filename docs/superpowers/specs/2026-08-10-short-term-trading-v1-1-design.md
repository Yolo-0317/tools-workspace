# A 股短线交易系统 v1.1 设计

## 1. 定位与边界

本系统是面向个人 A 股交易者的按需决策支持系统。系统计算候选、价格计划、组合风险、盘中信号和复盘结果，但不登录券商代替用户下单，不自动买入、卖出、撤单、转账或融资。

系统仅通过聊天对话和底层 CLI/JSON 接口使用：

- 不开发 Web 看板，不接入 Home Hub。
- 不设置后台定时任务，不主动推送。
- 用户发起“今日操作”“选股”“分析某股”“刷新持仓”“盘中验证”或“复盘”时，系统才运行所需链路。
- 用户在 Chrome 中自行登录东方财富证券后，系统可按用户指令读取持仓页面并刷新本地 MySQL；不保存券商密码、Cookie 或会话数据。
- 实际成交由用户明确告知，券商持仓刷新只用于核验账户结果，不根据持仓数量变化推断成交方向、价格或原因。

核心交易链路必须在 `AI_MODE=off` 时完整运行。AI 只能解释结构化结果，不能修改交易状态、价格、股数或风控决定。

## 2. v1.1 策略范围

v1.1 只实现“突破型试错”：

- 收盘候选只生成突破计划。
- 回踩、反转、连板接力和分歧转强不产生交易信号，仅保留未来版本扩展点。
- 首次试错金额为 2,000–4,000 元。
- 单笔计划最大亏损为 500 元。
- 总交易暴露上限为 40,000 元。
- 同题材暴露上限为 35,000 元。
- 同时新开交易最多 2 只；市场状态为 `LIMITED` 时最多 1 只。
- 8,000 元“强信号”上限在 v1.1 禁用，只有前向验证通过后的新规则版本才能启用。
- 主板按 100 股整数倍；科创板单笔不少于 200 股。

## 3. 统一状态机

### 3.1 收盘候选

```text
NO_TRADE -> WAIT_ENTRY
```

收盘后不得生成 `BUY_ALLOWED`。候选缺少日线、筹码、公告风险、市场状态或组合风控中的任一必填输入时，固定输出 `NO_TRADE`。

### 3.2 次日盘中

```text
WAIT_ENTRY -> WAIT_ENTRY
WAIT_ENTRY -> NO_TRADE
WAIT_ENTRY -> BUY_ALLOWED
```

只有价格触发、五项门禁、市场状态和组合风控全部通过时才能生成 `BUY_ALLOWED`。`BUY_ALLOWED` 自证据快照时间起有效 5 分钟，过期后必须重新采集和验证。

### 3.3 已有持仓

```text
HOLD -> HOLD
HOLD -> REDUCE
HOLD -> EXIT
REDUCE -> EXIT
```

跌破硬失效价优先输出 `EXIT`。`REDUCE` 必须包含明确股数或比例，并区分券商页面中的持仓数量与可用数量。

### 3.4 有效期

- 收盘计划最长有效到下一个交易日收盘。
- 计划更新必须创建新版本，不覆盖冻结的旧版本。
- 盘中 `BUY_ALLOWED` 最长有效 5 分钟。
- 证据过期、计划过期或规则版本不匹配时，状态自动降为 `NO_TRADE`。

## 4. 系统架构

```text
按需聊天意图
  -> orchestration
     -> source adapters
        -> MySQL 日线/股票基础信息
        -> Chrome 券商持仓
        -> OpenCLI 东财行情/板块/资金/筹码/盘口
        -> 正式公告引用
     -> snapshot store + freshness policy
     -> market regime
     -> selection
     -> trade plan
     -> portfolio risk
     -> intraday verifier
     -> decision freeze / journal / review
  -> chat renderer
```

模块边界：

- `contracts`：版本化对象和枚举。
- `repositories`：MySQL 持久化，不包含交易规则。
- `adapters`：外部来源解析和身份校验，不生成交易决定。
- `market_regime`：市场 `ALLOW/LIMITED/FREEZE`。
- `selection`：全市场突破候选，不输出买入信号。
- `diagnosis`：收盘价格计划。
- `risk`：账户、主题、名额和股数否决。
- `intraday`：冻结计划的盘中验证。
- `review`：计划、执行与后续结果对照。
- `orchestration`：按聊天意图组合模块，不含定时调度。
- `rendering`：将结构化结果输出为中文交易决策卡。

## 5. 版本化数据契约

所有对象必须包含：

- `schema_version`，v1.1 固定为 `1.1`。
- `as_of`，使用带时区的 ISO 8601 时间，内部统一为 UTC，展示为 Asia/Shanghai。
- `source` 和 `data_status`。
- 个股对象包含六位 `code`；市场对象不包含 `code`。
- 金额和价格在 Python 中使用 `Decimal`，JSON 使用字符串，MySQL 使用定点数。
- 每个写入对象具有 UUID 主键或明确的业务幂等键。

核心对象：

- `MarketStateV1`：交易日、指数状态、广度、成交额比、强势板块数、最终状态和原因。
- `CandidateV1`：代码、名称、候选类型、流动性、趋势、催化、板块、淘汰原因和证据引用。
- `EvidenceSnapshotV1`：快照类型、字段、来源、解析器版本、原始证据引用、新鲜度和质量状态。
- `TradePlanV1`：触发价、入场上限、回踩观察区、失效价、第一减仓参考、风险距离、有效期和规则版本。
- `RiskDecisionV1`：市场状态、账户敞口、主题敞口、名额、最大股数、允许状态和否决原因。
- `DecisionSnapshotV1`：候选、证据、计划和风控的 T 日不可变冻结快照。
- `IntradayDecisionV1`：盘中状态、通过/失败门禁、证据引用、最大股数和有效期。
- `TradeJournalV1`：用户明确确认的动作、数量、成交价、费用、原因和券商核验引用。
- `OutcomeObservationV1`：T+1/T+3/T+5 的价格、触发、最大有利/不利波动和数据状态。
- `PlanEvaluationV1`：规则版本、样本窗口、收益、风险、执行偏差和复盘标签。

未知字段拒绝写入；旧版本对象必须通过显式迁移函数升级，不能静默兼容。

## 6. 数据来源与放行规则

### 6.1 日线与股票基础信息

- `stock_daily` 是历史行情主源。
- 全市场目标交易日覆盖数量必须同时满足：不少于 5,000 只，且不少于之前 20 个交易日代码数中位数的 98%。
- 覆盖条件不满足时停止全市场新选股，但允许管理已有持仓。
- `stock_basic` 由现有 Tushare 凭据按需刷新，仅用于代码、名称、行业、上市日期、上市状态和 ST 名称风险；不用于实时价格或盘中交易证据。
- `stock_basic` 未就绪时只允许用户指定代码和已有持仓，不运行全市场选股。
- 自动目标日期必须来自 A 股交易日历，不能只按工作日推断。

### 6.2 券商账户

- 用户在 Chrome 中登录 `https://jywg.18.cn/Search/Position` 后发起刷新。
- 必须校验页面路径、账户脱敏标识、证券代码、字段数量和采集时间。
- 保存总资产、证券市值、可用资金、资金余额、冻结资金、持仓盈亏、当日盈亏，以及每只证券的持仓数量、可用数量、成本、现价、市值和盈亏。
- 不保存账户完整号码、登录凭据、Cookie 或浏览器会话。

### 6.3 收盘与盘中证据

- 公告风险：交易所、公司或巨潮正式披露为放行来源；东财只用于发现。无法保留正式来源链接时门禁不通过。
- 筹码：最近一个交易日的 90% 成本上下限、平均成本、获利比例和集中度。
- 行情：现价、涨跌幅、成交额、换手、量比和可验证分时成交序列。
- VWAP：仅根据可验证分时成交量价计算，不从页面文字估算。
- 板块：题材名称、涨幅、上涨比例、领涨股和成员关系。
- 资金：主力净流入及页面时间。
- 盘口：买一至买五、卖一至卖五和采集时间；连续三帧间隔至少 60 秒。
- 市场：三个指数、全市场广度、成交额比和强势板块数。

新鲜度固定为：行情/盘口 5 分钟，资金/板块/市场 15 分钟，筹码/日线/公告风险 1 个交易日，主题成员 7 个交易日。

## 7. 确定性交易规则

市场状态、候选门槛、五项门禁、价格公式和仓位公式以 `短线交易规则基线v1.md` 为规则来源。v1.1 补充以下解释：

- `ALLOW`：至少 2 个指数在 MA20 上方、广度不低于 50%、成交额比不低于 0.90。
- `FREEZE`：核心市场字段缺失；或至少 2 个指数在 MA20 下方且广度低于 40%；或成交额比低于 0.75 且广度低于 45%。
- 其余为 `LIMITED`。
- 候选必须满足 20 日平均成交额不低于 1 亿元、收盘价在 MA20 上方、MA5 不低于 MA10 且 MA10 不低于 MA20、当日涨跌幅处于 0%–7%。
- ST、停牌、上市不足 60 个交易日、正式高风险公告或不可退出标的固定淘汰。
- 突破触发、入场上限、硬失效、第一减仓参考和风险股数沿用规则基线中的公式。
- 五项盘中门禁为题材催化、板块共振、量价资金、筹码位置和盘口承接，缺一不可。

## 8. MySQL 存储

使用 `stock_data` 中独立的 `stt_` 表前缀：

- `stt_schema_versions`
- `stt_watchlist`
- `stt_market_states`
- `stt_candidates`
- `stt_evidence_snapshots`
- `stt_capture_attempts`
- `stt_source_health`
- `stt_daily_sync_runs`
- `stt_trade_plans`
- `stt_risk_decisions`
- `stt_decision_snapshots`
- `stt_intraday_decisions`
- `stt_outcome_observations`
- `stt_trade_journal`
- `stt_plan_evaluations`

约束：

- 迁移由 root 执行，运行时使用 `stt_app`。
- `stt_app` 保留业务读写权限，不保留 `DROP/ALTER/CREATE/INDEX`。
- 迁移必须幂等并记录版本。
- 决策快照和证据快照只追加，不允许原地修改。
- 当前有效计划可更新索引，但历史冻结快照不可覆盖。
- 原始页面正文和截图不写入 MySQL，只保存受控本地引用、摘要和校验值。
- 所有关键查询具备交易日、代码、状态和时间索引。

现有 `portfolio_account` 和 `portfolio_positions` 继续作为兼容读取入口；v1.1 增加可用数量、现价、市值、当日盈亏和券商采集时间字段，避免丢失页面事实。

## 9. 按需聊天工作流

- “刷新持仓”：读取用户已登录的券商页面，校验并写入账户/持仓快照。
- “今天该做什么”：刷新必要市场输入，读取持仓和有效计划，输出账户状态、必须处理项和可开名额。
- “收盘选股”：检查日线覆盖和基础信息，生成最多 5 只突破候选，再生成收盘计划和风险决定。
- “分析某股”：只处理指定代码，输出数据缺口或交易决策卡。
- “盘中验证”：只处理已有冻结计划和持仓，按需采集快变量并输出唯一主信号。
- “记录成交”：要求用户明确给出动作、数量、成交价和费用；随后可刷新券商页面核验持仓结果。
- “复盘”：生成计划与 T+1/T+3/T+5 实际结果、执行偏差和分组统计。

每次调用生成独立 `run_id`，相同幂等键的重试不重复生成业务记录。

## 10. 错误处理与安全降级

- MySQL 不可用：不生成新计划，不进行盘中放行。
- OpenCLI/Chrome 不可用：旧值只展示，不能通过门禁。
- 登录失效：停止券商刷新，要求用户在 Chrome 重新登录。
- 页面代码、时间或单位冲突：丢弃快照并记录解析失败。
- 同一页面字段连续两次失败：终止本轮采集。
- 同类页面 10 分钟窗口失败率超过 30%：熔断 10 分钟；由于系统无定时任务，下一次用户调用先执行健康探针。
- 任何异常不得自动放宽门禁、提高仓位或把缺失数据填为估算值。
- 日志必须屏蔽数据库密码、券商账户、Cookie 和页面会话信息。

## 11. 影子模式与验收

系统代码可完整计算 `BUY_ALLOWED`，但在数据源可靠性未达标前，`IntradayDecisionV1` 必须同时写入 `release_mode=SHADOW` 和 `actionable=false`。聊天窗口的主信号仍显示 `NO_TRADE`，并附加“影子规则命中，仅用于验证”的说明；不新增第七种交易状态。

解除影子模式必须同时满足：

- 至少 50 次独立采集。
- 行情成功率不低于 95%。
- 板块和盘口成功率分别不低于 90%。
- 关键字段完整率不低于 95%。
- 证券代码身份错配为 0。
- 至少 30 个冻结决策样本，覆盖 `ALLOW` 和 `LIMITED` 市场。
- 用户明确批准新规则版本启用正式 `BUY_ALLOWED`。

## 12. 测试与验证

- 契约测试：字段、枚举、Decimal、时区、未知字段和版本升级。
- 规则测试：所有阈值边界、价格公式、主板/科创板股数和状态转换。
- 仓储测试：迁移幂等、外键、唯一键、不可变记录和事务回滚。
- 解析器测试：每类来源使用脱敏 fixture，覆盖正常、缺字段、代码错配、时间过期和单位异常。
- 集成测试：在家庭 MySQL 中使用事务回滚验证 root 迁移和 `stt_app` 读写。
- 端到端测试：用户指定代码、全市场候选、持仓刷新、收盘计划、盘中验证、成交记录和复盘。
- 安全测试：输出、日志、异常和 Git 差异中不得出现密码、Cookie、完整券商账号或个人会话内容。

## 13. 分阶段交付

1. 数据契约、完整 DDL、仓储层和权限模型。
2. 交易日历、股票基础信息、市场环境、候选和收盘计划。
3. 公告、筹码、行情、VWAP、资金、板块和盘口采集及质量控制。
4. 组合风控、盘中状态机和持仓动作。
5. 决策冻结、交易日志、结果观察和前向复盘。
6. 聊天意图编排、中文决策卡、端到端验证和影子模式验收。

每一阶段都必须具备独立 CLI、版本化 JSON 输出、单元测试、MySQL 集成测试和明确降级状态。前一阶段未通过，不开始依赖它的下一阶段。
