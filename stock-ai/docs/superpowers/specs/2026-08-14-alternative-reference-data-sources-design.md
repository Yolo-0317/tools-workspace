# 买点选股替代参考数据源设计

日期：2026-08-14  
状态：用户已确认  
适用规则：`buy-point-selection-3.0.0`

## 1. 背景

买点优先 V1.3 需要三类点时参考事实：申万行业成员关系、每日 ST/停牌状态、重大公告风险。现有同步器依赖 Tushare `index_classify`、`index_member_all`、`stock_st` 和 `anns_d`，当前账号没有这些接口权限，导致三个数据集均以 `TUSHARE_PERMISSION_DENIED` 失败，正式候选按设计冻结。

本设计使用免费替代源补齐参考事实，同时维持以下纪律：

- 不调用、推荐或读取已弃用的东财八维/十一维 AI 框架；
- 不用当前名单反推历史，不允许未来数据泄漏；
- 关键数据缺失时正式候选为 0，观察层可以继续输出；
- 不自动下单，不新增定时任务；
- 历史回填范围为 2024-01-02 至最新完整交易日。

## 2. 范围

### 2.1 本次实现

- 巨潮资讯作为申万行业历史与公告风险主源；
- BaoStock 作为每日证券简称、ST 和停牌状态主源；
- 统一数据提供方接口、标准化、覆盖审计和安全错误码；
- 可断点、幂等的历史回填与手动增量同步；
- 让现有 V1.3 选股器继续读取既有标准化表，不感知外部数据源；
- 保留 Tushare 参考数据提供方代码为显式备用，但默认不调用。

### 2.2 不在本次范围

- 不改变 Tushare `daily` 日线主链路；
- 不扩大公告风险关键词、严重级别或风险持续期；
- 不重新设计三类买点形态、排序、仓位和退出规则；
- 不创建自动刷新、推送或券商委托任务；
- 不因参考数据补齐而绕过历史验证和 20 日前向晋级门槛；
- 不把上交所、深交所公告接口同时做成第三套生产主源，后续仅在确有必要时增加交叉校验。

## 3. 数据源决策

| 数据集 | 主源 | 传输实现 | 点时语义 | 备用 |
| --- | --- | --- | --- | --- |
| 申万行业分类字典 | 巨潮资讯 | 隔离的 AKShare 巨潮接口适配器 | 分类代码及终止日期 | 无自动备用 |
| 个股行业历史变更 | 巨潮资讯 | 隔离的 AKShare 巨潮接口适配器 | 变更日期及分类标准 | Tushare 仅可显式启用 |
| 全市场公告 | 巨潮资讯 | 巨潮官方分页 HTTP 适配器 | 公告发布时间、ID、官方链接、总数与总页数 | 无自动备用 |
| 每日简称与交易状态 | BaoStock | 官方 Python SDK | 指定交易日快照 | 无自动备用 |
| 日线行情 | 现有 Tushare `daily` | 现有同步器 | 完整交易日日线 | 不变 |

AKShare 仅作为巨潮行业公开接口的传输封装，适配器只允许调用巨潮相关函数，不允许调用任何东财、同花顺或其他混合来源函数。公告适配器直接读取巨潮官方分页接口，以保留 `totalAnnouncement`、当前页和总页数供完整性核对。标准化事实的 `source` 必须写 `CNINFO` 或 `BAOSTOCK`，不能写成 AI 结果，也不能伪装成交易所原始接口。

允许的 AKShare 函数固定为 `stock_industry_category_cninfo` 和 `stock_industry_change_cninfo`。BaoStock 固定使用带 `day` 参数的 `query_all_stock`。适配器不得根据函数缺失自动切换到同名的东财或同花顺数据。

## 4. 架构

### 4.1 提供方边界

新增统一 `ReferenceProvider` 边界，外部提供方只负责返回原始、可验证的结构化记录：

- `CninfoReferenceProvider`
  - 读取申万分类字典；
  - 读取单只股票的行业历史变更；
  - 按日期分页读取全市场公告；
- `BaoStockReferenceProvider`
  - 登录和登出会话；
  - 按指定交易日读取全市场代码、简称和交易状态；
- `TushareReferenceProvider`
  - 保留当前能力用于显式备用；
  - 默认配置下不实例化、不探测权限、不影响主流程。

提供方不能写数据库、判定候选资格或修改交易规则。标准化、点时区间、覆盖率和持久化由同步服务统一处理。

### 4.2 同步服务

同步服务接受起止交易日和提供方组合，执行：

1. 从 MySQL `stock_daily` 加载区间内交易日及主板股票全集；
2. 读取巨潮申万分类字典；
3. 为主板股票逐只补齐行业变更历史；
4. 为每个交易日读取 BaoStock 全市场快照；
5. 为每个自然日读取巨潮公告全部分页；
6. 标准化事实并计算覆盖；
7. 事务内幂等写入事实和同步审计；
8. 只有满足完整性条件的数据集才能写 `COMPLETE`。

`select_short_term_candidates.py --refresh-reference-data` 继续调用同一个手动同步入口，但默认提供方改为 `cninfo-baostock`。普通选股仍只读缓存，不隐式联网。

## 5. 点时标准化

### 5.1 申万行业

行业变更请求必须覆盖股票上市后历史，至少包含 2024-01-02 之前最后一条有效记录，不能只请求回测起始日之后的变化。同步器仅保留“申银万国行业分类标准”，并使用巨潮分类字典把行业代码归一到一级行业。

对同一股票按变更日期升序生成区间：

- `valid_from` 为变更生效日期；
- 下一条记录出现时，上一条 `valid_to` 为下一变更日期之前的最后一个确认交易日；
- 没有下一条时 `valid_to` 为空；
- 重叠区间、空行业代码、无法映射一级分类或同日冲突均使该股票行业同步失败。

分析日主板股票行业覆盖率低于 98% 时，`sector` 数据集不得标记完整。即使总体达到 98%，没有行业成员关系的个股仍只能进入观察层。

### 5.2 ST 与停牌

BaoStock 按交易日返回代码、`code_name` 和 `tradeStatus`：

- 证券简称按去空格和大小写归一后，以 `ST`、`*ST`、`S*ST` 等风险警示前缀识别 ST；
- `tradeStatus=0` 生成当日 `SUSPENDED` 风险标记；
- ST 和停牌标记均只对返回快照对应交易日有效；
- 不根据 5% 涨跌幅、当前简称或后续公告推测历史 ST。

当日 BaoStock 主板代码对 MySQL 当日主板全集覆盖低于 98%，或响应日期、字段、代码格式异常时，`st` 数据集不得标记完整。停牌事实与 ST 事实可共存。

### 5.3 重大公告

巨潮按自然日读取全市场公告，必须验证接口声明总数、总页数、每页编号和公告 ID 去重。普通公告不落业务事实表，只计入完整性审计；命中现有重大风险词的公告写入 `buy_point_risk_flags`，并保留公告 ID 和巨潮官方链接作为证据。

生效日期规则：

- 交易日 15:00:00 及以前发布：当日生效；
- 交易日 15:00:00 以后发布：下一交易日生效；
- 非交易日发布：下一交易日生效；
- 缺少可靠发布时间：保守地从下一交易日生效。

首版沿用现有标题分类、严重级别和持续期，不新增关键词。全量分页成功但总数为 0 可以视为合法空结果；网络异常、分页缺失、总数不一致或字段变化不能视为完整。

“沿用持续期”具体指保持现有 `effective_to=None` 语义；本次只校正 `effective_from` 的点时边界，不擅自把重大风险缩短为固定天数。

## 6. 持久化与审计

复用：

- `buy_point_sector_memberships`
- `buy_point_risk_flags`
- `buy_point_reference_sync_runs`

新增一条独立、可幂等执行的增量迁移，为同步审计增加：

- `provider VARCHAR(32)`：实际提供方；
- `expected_count INT`：期望覆盖对象或公告总数；
- `coverage_ratio DECIMAL(7,6)`：主板覆盖率；
- `details_json JSON`：分页数、完成数、失败代码数和检查点摘要。

同一迁移新增 `buy_point_reference_checkpoints`，字段固定为：

- `provider`、`dataset`、`partition_key` 联合主键；
- `cursor_value`：公告当前页等可继续游标；
- `status`：`RUNNING / COMPLETE / FAILED`；
- `error_code`、`details_json` 和 `updated_at`。

行业的 `partition_key` 为六位股票代码，ST/停牌和公告的 `partition_key` 为 ISO 日期。审计表只保存批次汇总，检查点表负责精确续跑，避免把数千个代码塞进单个 JSON 字段。

已应用的 `015_buy_point_reference_history.sql` 不回写修改。新迁移只增加可空列，并由新同步器完整写入；旧审计记录保持可读。

事实写入继续使用稳定主键和幂等 upsert。重复同步同一区间不得产生重复成员关系或风险标记。失败运行只能写 `FAILED` 审计，不能写覆盖完成记录。

## 7. 回填、断点与限流

首次回填范围固定为 2024-01-02 至最新完整交易日：

- 行业按股票设置检查点；
- ST/停牌按交易日设置检查点；
- 公告按自然日和页码设置检查点；
- 已完整数据默认跳过；
- 显式刷新时重新抓取最近两个交易日，处理补发、更正和延迟更新；
- 中断后从最后成功检查点继续，不删除已经验证的事实。

巨潮使用低并发和最小请求间隔，遇到 429、5xx 或暂时网络失败时指数退避；达到重试上限后记录安全错误码并停止对应数据集。不得通过不受控并发规避提供方限制。BaoStock 登录、查询和登出分别审计，查询失败不能用上次会话结果补齐。

## 8. 失败关闭与错误码

稳定错误码固定包括：

- `PROVIDER_UNAVAILABLE`
- `PROVIDER_RATE_LIMITED`
- `PROVIDER_SCHEMA_CHANGED`
- `PROVIDER_AUTH_FAILED`
- `PAGE_COUNT_MISMATCH`
- `COVERAGE_BELOW_THRESHOLD`
- `INDUSTRY_HISTORY_INCOMPLETE`
- `CHECKPOINT_INCOMPLETE`

错误详情只保存提供方、端点类别、日期、页码、HTTP 状态或 SDK 错误码；不保存环境变量、令牌、Cookie 或完整响应头。

当天任何关键数据集不是 `COMPLETE` 时：

- 正式候选为 0；
- 技术形态可以进入准备中观察；
- 报告明确列出 `SECTOR`、`RISK_COVERAGE` 或 `SUSPENSION_COVERAGE` 缺口；
- 旧 Tushare 数据、旧日期缓存和影子策略不能覆盖缺口。

## 9. 测试

### 9.1 单元测试

- 巨潮分类字典和行业变更字段映射；
- 一级行业归一与相邻有效区间；
- BaoStock 代码、简称、ST 前缀和停牌状态；
- 公告风险词与 15:00 生效边界；
- 非交易日和缺失时间的下一交易日映射；
- 提供方错误到安全错误码的映射。

### 9.2 契约与仓储测试

- 公告分页缺页、重复公告和总数不一致；
- 行业覆盖和 BaoStock 日期覆盖低于 98%；
- 断点续跑和重复同步幂等；
- 失败运行不产生 `COMPLETE`；
- 新旧审计行兼容读取；
- 同一分析日只能查询当时已生效的事实。

### 9.3 联网验收

联网测试默认不随单元测试运行，必须显式启用：

1. 同步最近两个完整交易日；
2. 抽查至少一只普通股票、一只 ST 股票、一只停牌股票和一只重大风险公告股票；
3. 核对巨潮官方链接、发布时间和行业分类；
4. 核对覆盖审计和重复执行结果；
5. 小范围通过后再启动 2024-01-02 至最新日期的完整回填。

## 10. 发布与成功标准

发布顺序：

1. 增量迁移和新适配器测试通过；
2. 最近两个交易日联网验收通过；
3. 完整历史回填并核对覆盖；
4. 重新执行 V1.3 手动全市场选股；
5. 确认候选不再因 `SECTOR`、`RISK_COVERAGE` 或停牌覆盖缺失而统一降级；
6. 运行时间顺序历史验证；
7. 继续累计至少 20 个不同手动前向交易日和 20 个已解析计划。

参考数据补齐只解除数据缺口，不等于策略具备正期望，也不自动把发布模式从 `SHADOW` 改为 `LIVE`。只有历史冻结测试和前向门槛全部通过后才能正式晋级。
