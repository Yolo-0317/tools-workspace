# 文学稿候补草稿槽位设计

## 目标

在公众号草稿箱中同时保留两篇尚未发表的文学稿，避免新稿覆盖现有 `literary` 槽位中的《徐霞客游记》。本次将《道德经》放入新的受管理槽位 `literary_next`。

## 方案

- 保留现有 `literary` 槽位及其媒体 ID，不做删除或更新。
- 新增固定槽位键 `literary_next`，与 `literary` 一样纳入受管理草稿集合。
- 文学稿校验允许 `literary` 和 `literary_next` 两个槽位，拒绝其他任意槽位名。
- 文学稿渲染与推送保留稿件自身的 `slot_key`，不再强制改回 `literary`。
- 《道德经》结构化稿件的 `slot_key` 改为 `literary_next`，现有双确认工作流继续使用该稿件。

## 数据流

文学稿 JSON 指定 `slot_key` → 文学稿加载器校验允许值 → 富文本构建保留该槽位 → 浏览器写稿流程将槽位传给草稿更新器 → 草稿更新器只替换相同槽位的旧草稿。

因此推送《道德经》时，只会创建或替换 `literary_next`，不会触碰 `literary`。

## 清理与兼容性

- `literary_next` 加入草稿清理流程的保留集合，防止被识别为额外草稿后删除。
- 既有未指定槽位的文学稿仍默认使用 `literary`，现有流程不变。
- 两个文学槽位均只写入草稿箱，不自动发表。

## 验证

- 先增加失败测试，证明当前代码拒绝 `literary_next`。
- 验证文学稿加载、渲染和推送链路均保留 `literary_next`。
- 验证受管理槽位集合包含 `literary_next`。
- 运行文学稿、浏览器写稿和草稿槽位相关测试。
- 推送前读取槽位登记，确认《徐霞客游记》的 `literary` 媒体 ID 未变化。
