# DeepSeek 涨价热点商业稿设计

## 目标

为「牛马也智能」新增的 `hot_business` 稿型制作一篇当日热点商业长图文，主题为 DeepSeek API 正式调价。文章不把“涨价”停留在价格表复述，而是解释模型服务从低价获客转向价值定价时，开发者真正支付的成本发生了什么变化。

本轮先完成研究、成稿、公开配图和干跑质检；干跑通过后再更新独立的 `hot_business` 微信草稿槽位，不发表文章，也不影响普通 `hotspot` 槽位。

## 选题与标题

标题暂定：`DeepSeek涨价，低价牌打完了吗？`

文章只回答一个商业问题：DeepSeek 为什么在低价已成为品牌标签后提高 API 价格，它正在从“便宜 token”转向销售什么？

核心判断：涨价不必然意味着 DeepSeek 放弃性价比，而更像模型服务从单纯比较 token 单价，转向比较完成同一任务所需的 token、等待时间、稳定性和工程迁移成本。低价可以快速打开开发者市场，却未必能够长期覆盖高性能模型、长上下文和高并发服务的持续投入。

标题中的“低价牌打完了吗”是待论证的问题，不在标题或正文中预设“暴涨”“割韭菜”“算力不足”等未经证实的结论。

## 事实与来源边界

正文至少使用三个不同来源域，其中必须包括 DeepSeek 官方定价页或版本公告。研究按以下顺序取材：

1. DeepSeek 官方当前定价页，用于确认当前模型、上下文、缓存命中、缓存未命中、输出 token 价格和并发限制；
2. DeepSeek 官方历史版本或价格公告，用于确认可比较的旧口径；
3. 两家独立公开媒体或行业来源，用于补充开发者反应、行业对比和商业背景。

任何涨幅必须由同币种、同模型层级、同 token 类型和同计费口径计算。无法找到同口径旧价格时，只写当前价格，不写百分比涨幅。

正文明确区分：

- `facts`：官方页面或报道直接支持的事实；
- `inferences`：由多个事实推导的商业判断，并使用“更像”“可能”“从公开定价看”等边界词；
- `rejected_claims`：算力短缺、融资压力、用户流失、利润变化等缺少公开证据的说法，不进入正文核心论点。

## 正文结构

正文为 2300 至 2700 个去空白中文字符，使用纯段落，不设编号标题或报告式小标题。

叙事顺序：

1. 前 80 字交代 DeepSeek 正式调价及最反常的一点：低价曾是其最强品牌记忆；
2. 用同口径价格说明到底调整了什么，不堆完整参数表；
3. 解释 token 单价为什么不是企业实际使用大模型的全部成本；
4. 拆解模型能力、缓存、输出长度、并发、稳定性和迁移成本如何共同影响总账单；
5. 判断 DeepSeek 的商业竞争正从“最低价格”转向“单位任务成本与工程效率”；
6. 落到个人开发者、中小团队和大客户各自受到的不同影响；
7. 以一个具体讨论问题收束，不写关注诱导。

## 完读率设计

这篇稿优先修复近期文章完读偏低的问题，执行以下硬约束：

- 标题前 15 字完整出现 `DeepSeek涨价` 和核心疑问；
- 首段 80 字内同时出现事件、变化和读者利益点，不从行业背景讲起；
- 前 300 字完成“发生了什么、为什么值得继续看、文章要回答什么”三个任务；
- 段落以 1 至 3 行为主，避免连续五段句长相同；
- 每 300 至 500 字至少放置一个节奏钩子：价格反差、具体账单、短句落锤、轻问句或开发者场景；
- 至少提供两个可直接转述的颗粒，例如同口径价格变化和“token 单价低不等于任务总成本低”；
- 技术解释必须落到一个具体调用场景，不连续展开术语定义；
- 一张封面加三张正文图，正文图均匀分布，作为滚动阅读换气点；
- 文末只留一个站队问题，稿末关注与推荐提示仍由现有流水线注入。

完读干跑的验收信号包括：阅读量自动清单 21/21、正文无超长段落、前 220 字有具体数字、文末有互动问句、标题与首段同题。质量门槛为总分不低于 75、AI 味不高于 20、无合规红线。

## 完读规则持久化

本次完读约束不能只存在于这一篇设计稿中。实施时同步更新 `.cursor/skills/wechat-mp-writing/traffic-copy-craft.md`，新增“热点长图文完读硬约束”，作为以后 `hotspot` 与 `hot_business` 写稿、改稿和质检的默认规则；其他长图文稿型可复用节奏要求，但保留各自的篇幅与结构模板。

持久规则包括：

- 首段 80 字内交代事件、变化和读者利益点；
- 前 300 字完成事实、悬念和文章核心问题；
- 每 300 至 500 字出现一个新的信息增量或节奏钩子；
- 至少两个可转述颗粒；
- 段落多数为 1 至 3 行，避免连续五段同句长；
- 正文配图均匀分布，承担滚动阅读换气；
- 文末只留一个具体互动问题，不把关注诱导写进正文。

同时更新 `scripts/tools/wechat_mp_hot_business_article.py` 的写作提示，使自动生成的热点商业稿直接遵守上述规则，而不是等成稿后再人工补救。现有 `wechat_mp_traffic_checklist.py` 能覆盖的标题、开篇数字、超长段落和互动问句继续作为自动项；暂时无法可靠自动判断的“信息增量”“可转述颗粒”和配图节奏，写入干跑人工审阅清单，不为了本篇新增脆弱的关键词计数规则。

## 配图

配图优先使用 DeepSeek 官方版本公告、官方产品界面或公开媒体报道中的可追溯图片。微博和百度只作为发现入口；图片必须回到原始页面，记录页面 URL、图片 URL、来源、发布时间和核验状态。

目标为一张封面和三张正文图。避免四张都使用价格表截图，画面分别承担：品牌与事件、价格变化、开发者使用场景、行业竞争。只有无法获得足够的可核验公开图时，才按 `codex-image-request.json` 对缺失槽位生成原创解释图。

## 热点商业数据契约

输出写入 `output/hot_business_deepseek_price_20260817.json`，必须包含：

- `title`、`digest`、`body`、`topic`；
- 至少三个不同域名的 `research_urls`；
- 不少于 20 字的 `original_thesis`；
- 单一 `business_question`；
- 每条含 `claim` 与 `source_url` 的 `facts`；
- 明确标注边界的 `inferences`；
- 本次未采用的 `rejected_claims`；
- 固定 `slot_key: "hot_business"`。

## 推广与草稿边界

`hot_business` 尝试自动选择一部题材不冲突、综合收益较高的短剧。短剧池、归因或候选不可用时采用该稿型已有的软失败策略，文章仍可进入草稿；如果插入组件，则正式保存后必须回读确认恰好一个 `short-play`、没有普通 CPS 商品卡且归因票据存在。

正式推送只更新 `hot_business` 独立槽位，不调用发表接口。用户仍需在微信后台预览图片、排版和短剧卡后人工决定是否发表。

## 验收

1. 当前价格、历史价格和涨幅比较均能回溯且口径一致；
2. 正文去空白长度在 2300 至 2700 字之间，纯段落，无报告式小标题；
3. 至少三个独立来源域，关键事实全部映射到来源；
4. 原创增量门禁通过，质量分不低于 75，AI 味不高于 20，无合规失败；
5. 阅读量自动清单 21/21，并满足完读率设计中的节奏与可转述颗粒要求；
6. 一张封面和三张正文图均可追溯，或仅对无法补齐的槽位使用原创解释图；
7. `hot_business` 槽位更新成功，普通 `hotspot` 槽位不变；
8. 如有短剧卡，远端回读为一个短剧卡、零个普通商品卡，归因有效。
9. `traffic-copy-craft.md` 已包含热点长图文完读硬约束，`hot_business` 写作提示已引用同一组要求，并有相应单元测试防止回退。
