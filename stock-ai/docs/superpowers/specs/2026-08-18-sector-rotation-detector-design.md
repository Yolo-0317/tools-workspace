# 全市场强势板块轮动检测模块设计

日期：2026-08-18

## 1. 背景与目标

现有系统已经具备东财行业板块涨幅榜采集、申万行业成员数据、个股日线、板块共振门禁、持仓读取和统一调度能力，但这些能力分散在公众号选题、买点研究和日常选股链路中，尚不能回答短线交易中的核心问题：哪些产业方向正在从潜伏转为启动，哪些已经确认，哪些虽然排名靠前但已不宜追高。

第一版新增独立的手动板块轮动检测模块。模块从全市场细分行业中动态选择六个值得关注的产业链方向，保存跨次、跨日快照，并在每个方向内保留最多十只观察股和最多三只正式交易候选。

本模块的目标是提高短线机会发现效率并降低追高风险，不替代现有综合选股，不修改投顾阶段、仓位上限或持仓记录，不自动推送，不生成或执行交易订单。

## 2. 已确认范围

- 只提供手动命令，第一版不接 Docker scheduler、launchd、Home Hub 或消息推送。
- 扫描全市场细分行业，但不展示全量行业；只输出动态六方向轮动核心池。
- 细分行业参与评分，同一产业链的重复行业自动合并。
- 六方向固定结构为三个当前最强、两个正在增强、一个回踩观察。
- 每个方向最多列十只观察股，其中最多三只成为正式交易候选。
- 三类正式候选角色为龙头、补涨、回踩；同一股票在同次运行中只占一个角色。
- 报告提供观察价、触发价、禁追价和失效位，但不生成订单。
- 运行、板块快照和候选结果写入 MySQL，并生成 Markdown 报告。
- 阈值配置化。第一版是待验证规则，不宣称已完成收益验证。

## 3. 非目标

- 不将板块评分直接写入 `selection_daily_results`。
- 不改变 `combined`、`dual_pool`、`ma5`、`five_factor` 或现有买点策略的排序。
- 不把公众号行业稿脚本改造成交易模块。
- 不使用旧东财八维或十一维个股诊断。
- 不将单个涨停股、单条消息或概念标签视为板块启动的充分条件。
- 不在第一版实现自动回测调参、自动仓位计算或自动下单。

## 4. 方案选择

采用独立 `sector_rotation` 模块，而不是扩展公众号行业榜脚本或直接并入综合选股。

独立模块复用现有客观数据采集和买点基础规则，但拥有自己的领域模型、历史快照、状态机和报告。这样可以单独验证板块信号质量，避免未经验证的热点倾向污染现有选股结果，也为后续接入看板或调度保留清晰边界。

## 5. 模块边界

建议新增：

- `stock_ai/sector_rotation/models.py`：运行、板块、产业链、候选和价位模型。
- `stock_ai/sector_rotation/normalization.py`：细分行业过滤、别名标准化和产业链归并。
- `stock_ai/sector_rotation/scoring.py`：板块五维评分、过热惩罚和状态判定。
- `stock_ai/sector_rotation/selection.py`：六方向选择、十股观察池和三类候选选择。
- `stock_ai/sector_rotation/pricing.py`：观察价、触发价、禁追价和失效位计算。
- `stock_ai/sector_rotation/repository.py`：MySQL 读写和历史快照读取。
- `stock_ai/sector_rotation/reporting.py`：Markdown 报告。
- `stock_ai/sector_rotation/service.py`：单次运行编排。
- `scripts/analysis/detect_sector_rotation.py`：唯一手动 CLI 入口。

继续复用：

- `scripts/tools/fetch_eastmoney_quotes.py`：东财行业榜、板块成分及盘中客观行情。
- `scripts/tools/portfolio_db.py`：MySQL 连接、日线、行业成员和持仓读取。
- `stock_ai/buy_point_selection` 中可稳定复用的反追高、结构和板块门禁纯函数。

公众号脚本可以继续读取同一东财行业榜，但不得成为本模块的反向依赖。

## 6. 数据流

手动命令每次执行以下步骤：

1. 创建运行记录，确定 `intraday` 或 `close` 行情口径。
2. 读取东财行业板块排名、涨跌幅、领涨股和板块代码。
3. 读取相关板块成分及盘中行情；读取 MySQL 最近二十至六十个交易日的日线、成交额、行业成员和当前持仓。
4. 过滤导航项、指数项、无有效成分项和流动性不足项。
5. 将细分行业标准化并归并为产业链方向。
6. 为每个产业链计算强度、宽度、成交额、连续性、结构质量和过热惩罚。
7. 结合历史快照判定潜伏、启动、确认、过热或退潮。
8. 按固定配额选出六个轮动方向。
9. 为每个方向生成最多十只观察股及最多三只正式候选。
10. 计算条件价，写入 MySQL，并输出 Markdown 报告。
11. 若关键数据不完整，保存失败或降级状态；禁止用旧行情冒充实时结论。

## 7. 行业标准化与产业链归并

原始细分行业必须保留在快照中，报告展示的是归并后的产业链方向。

归并由显式配置驱动，不使用不可解释的语言模型临时分类。配置至少包含：

- 标准产业链代码与名称；
- 原始行业名称、别名和关键词；
- 排除词；
- 行业归属优先级；
- 允许共存的相邻方向。

例如“种子、粮食种植、其他种植业、种植业”归并为“农业种植”。“半导体材料”和“集成电路封测”可共同归入电子产业链大类，但在有足够独立成分和强度时允许作为不同交易方向共存。为防止单条产业链占满名单，同一大类默认最多进入一个六方向名额；只有两个子方向均满足确认状态且成分重叠低于配置阈值时才允许并存。

无法归并的有效行业使用稳定的规范化原名，不因缺少映射而直接丢弃；报告标记为“待归类”。

## 8. 板块评分

板块基础分满分一百分：

- 相对强度三十分：当日涨幅分位、排名分位和较上次快照的排名变化。
- 板块宽度二十五分：上涨家数比例、站上 MA5/MA20 的成员比例和强化成员数量。
- 成交额二十分：板块成交额相对五日均值、上涨成员成交额占比。
- 连续性十五分：连续增强次数、连续强势交易日和状态稳定度。
- 结构质量十分：龙头、跟随和补涨扩散是否同时存在，是否由单一股票贡献绝大多数强度。

过热惩罚单独计算并从基础分扣除，最高扣三十分。默认触发条件包括：

- 板块单日涨幅或五日累计涨幅超过配置阈值；
- 板块成员相对 MA5 的中位乖离过大；
- 涨停或大涨集中于极少数成员；
- 龙头已明显加速而跟随宽度下降；
- 板块排名很高但成交额或上涨家数不支持。

所有分项、原始值、阈值版本和扣分理由必须入库，保证报告可解释和后续可回放。

## 9. 状态机

状态必须结合当前评分和历史快照判定，不能只根据当前排名贴标签。

- `LATENT` 潜伏：尚未进入最强区，但宽度、成交额或排名连续改善，且未过热。
- `STARTING` 启动：首次同时通过强度、宽度和成交额门槛，结构质量合格。
- `CONFIRMED` 确认：连续两个有效快照或连续两个交易日保持启动条件，没有触发过热门禁。
- `OVERHEATED` 过热：基础强度较高，但短期涨幅、乖离或龙头集中度触发反追高门禁。
- `FADING` 退潮：此前为启动或确认，随后综合分明显下降，或宽度、成交额、龙头承接至少两项恶化。

同一交易日的多次手动运行可用于盘中状态迁移；若只有每日一次运行，则使用相邻交易日快照。缺少前序快照时，不允许直接判定确认，只能判定潜伏、启动或过热。

## 10. 六方向轮动核心池

输出名额固定为：

- 当前最强三个：只从启动或确认中选择；过热方向不占正式机会名额。
- 正在增强两个：只从潜伏中选择，优先连续改善且未出现大幅拉升的方向。
- 回踩观察一个：此前确认、当前缩量回踩，尚未进入退潮。

排序先比较状态优先级，再比较扣除过热惩罚后的综合分、宽度、连续性和结构质量。产业链去重在名额分配前执行。

如果某个类别不足，不用低质量板块强行补满；报告可以少于六个方向，并明确缺口原因。

## 11. 每方向十股观察池

每个入选方向最多保留十只：

- 两只核心龙头；
- 三只正在增强的跟随股；
- 三只尚未大幅拉升的补涨观察股；
- 两只处于趋势回踩的观察股。

同一股票只出现一次，按“正式候选资格优先、角色质量优先、综合分优先”去重。实际数量不足时不补入低流动性或风险标的。

观察池展示至少包括：代码、名称、角色、当日涨幅、近五日涨幅、成交额比、MA5/MA20 位置、与板块相对强弱、过热标记、是否当前持仓和未入正式候选的理由。

涨停、单日涨幅过大或乖离过大的股票可以作为龙头强度样本保留，但只能标记为“强度观察、禁止追高”。

## 12. 正式交易候选

每个方向最多三只：

- 龙头候选：板块核心、流动性合格、未触发个股过热门禁。若龙头过热，只保留观察角色，不强行产生龙头正式候选。
- 补涨候选：趋势不弱于 MA20，板块增强时个股尚未大幅加速，成交额和相对强度开始改善。
- 回踩候选：已有上升结构，回踩平台、MA5 或 MA10 附近，缩量且未跌破结构失效位。

正式候选必须通过现有风险标记、流动性、个股反追高和板块状态门禁。当前持仓只增加 `held` 标记，不自动提高排名，也不绕过门禁。

## 13. 条件价

仅为正式候选计算：

- 观察价：接近关键平台、均线或回踩区后开始关注的价格。
- 触发价：突破结构位或回踩承接成立的条件价。
- 禁追价：超过后盈亏比显著恶化，不再新开仓的价格。
- 失效位：跌破后取消候选的结构价。

价位优先使用可解释的二十日结构高低点、MA5/MA10/MA20 和 ATR 缓冲计算。必须满足多头候选的基本顺序和最小风险收益约束；无法得到可靠结构时，不输出猜测价位，候选降级为观察。

默认个股反追高门禁包括单日涨幅超过 7%、近五日涨幅超过 15%或距离 MA5 超过 5%。这些是首版配置默认值，不是不可修改的硬编码常量。

## 14. MySQL 数据模型

### 14.1 `sector_rotation_runs`

主要字段：

- `run_id`；
- `observed_at`、`trade_date`、`edition`；
- `status`、`data_freshness`、`threshold_version`；
- `raw_sector_count`、`normalized_chain_count`、`selected_chain_count`；
- `error_code`、`error_message`；
- `created_at`。

### 14.2 `sector_rotation_snapshots`

主要字段：

- `run_id`、`chain_code`、`chain_name`；
- `raw_sector_codes_json`、`raw_sector_names_json`；
- `state`、`bucket`、`rank_no`、`score_total`；
- 五项分数、过热扣分和对应原始指标；
- `state_reasons_json`、`data_complete`；
- `created_at`。

同一运行与产业链唯一。

### 14.3 `sector_rotation_candidates`

主要字段：

- `run_id`、`chain_code`、`ts_code`、`name`；
- `pool_rank`、`role`、`formal_eligible`、`held`；
- 当前价、涨跌幅、近五日涨幅、成交额比、均线与乖离；
- `watch_price`、`trigger_price`、`no_chase_price`、`invalidation_price`；
- `reasons_json`、`rejection_reasons_json`、`raw_json`；
- `created_at`。

同一运行、产业链和股票唯一。

迁移文件遵循 `stock-mysql/sql/` 现有编号与初始化约定，不修改既有表含义。

## 15. CLI

默认命令：

```bash
.venv/bin/python -m scripts.analysis.detect_sector_rotation
```

支持参数：

```text
--edition auto|intraday|close
--top-sectors 6
--stocks-per-sector 10
--output <path>
--no-db
```

`auto` 根据运行时间和交易日决定盘中或收盘口径，但报告始终打印实际采用的行情时间。`--no-db` 用于只读预览，不读取跨次状态时必须在报告中注明状态判定能力受限。

成功退出码为零；行情源失败、日线严重过期或数据库写入失败使用非零退出码。允许降级的局部缺失仍返回零，但报告和运行记录必须列出缺失范围。

## 16. Markdown 报告

报告文件默认写入：

```text
output/sector_rotation_YYYYMMDD_HHMM.md
```

报告依次包含：

1. 数据时间、行情口径和完整性；
2. 六方向轮动核心池总览；
3. 相较上次运行的状态迁移；
4. 当前持仓与强势方向交集；
5. 每个方向最多十只观察股；
6. 每个方向最多三只正式候选及四类条件价；
7. 过热板块与禁止追高名单；
8. 退潮板块；
9. 数据限制、阈值版本和非自动交易声明。

报告首先解释为什么入选或淘汰，再展示分数。禁止把综合分直接翻译为确定性买入结论。

## 17. 错误处理与数据新鲜度

- 东财行业榜不可用：整次运行失败，不使用公众号缓存或历史榜单冒充当前榜单。
- 部分板块成分不可用：受影响方向标记不完整，不生成正式候选。
- MySQL 日线落后：盘中可使用上一交易日日线加实时行情计算，但必须标注；收盘后若当日日线尚未同步，也要打印该口径。
- 历史快照缺失：禁止判定确认和退潮，只允许潜伏、启动或过热。
- 当前持仓读取失败：继续完成全市场检测，但持仓交集标记为未知。
- 数据库写入失败：不把仅生成的本地报告描述为成功落库，命令返回非零。
- 单只股票价位数据不完整：降级为观察股，不输出条件价。

## 18. 测试策略

单元测试至少覆盖：

- 行业别名、排除词和产业链归并；
- 同产业链名额去重和允许共存条件；
- 五项评分、过热扣分和阈值版本；
- 潜伏、启动、确认、过热、退潮状态迁移；
- 单一龙头大涨但板块宽度不足时不得启动；
- 六方向配额不足时不得低质量补位；
- 十股观察池角色配额和去重；
- 三类正式候选及个股反追高门禁；
- 四类价位的顺序、结构约束和缺失降级；
- 当前持仓标记不改变候选门禁；
- 报告内容和失败提示。

数据库集成测试覆盖三张新表的幂等写入、唯一约束、历史快照读取和失败回滚。CLI 测试使用固定行业榜、成分股、日线和持仓夹具，不依赖实时网络。

## 19. 验收标准

第一版完成时必须满足：

- 一条手动命令可以完成检测并生成报告；
- 报告最多输出六个去重后的产业链方向；
- 每方向最多十只观察股、最多三只正式候选；
- 所有正式候选均有可解释理由和完整条件价，或明确降级；
- 过热方向和过热个股不会进入正式新开仓候选；
- 运行、板块和候选历史可以从 MySQL 回读；
- 数据缺失不会生成伪实时结论；
- 不修改现有选股、持仓、监控规则或订单状态；
- 最相关单元与集成测试通过。

## 20. 后续评估

第一版至少积累二十个交易日后，再按信号发生后的一个、三个和五个交易日收益，分别评估板块状态、候选角色、最大有利波动、最大不利波动和触发后盈亏比。

只有在信号稳定性得到验证后，才讨论接入自动调度、Home Hub、消息推送或将板块状态作为综合选股过滤条件。自动化接入不属于本设计的第一版范围。
